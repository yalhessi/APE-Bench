# PR 30650 review notes (condition C)

- `Mathlib/Util/AddRelatedDecl.lean` `addRelatedDecl`: the value passed to `construct` is now `.const src us` rather than `info.value!`. That is sound: the new lemma references `src` instead of re-checking its proof, and it also stops `value!` panicking on constants that have no body. Its inferred type is exactly `info.type`, so the callback no longer needs the type. The docstring's `construct type value levels` bullet was not updated, which is finding 1. It also omits `to_app`, which is older than this PR. The `defnDecl` branch copies `hints` from `src` even though the value now references `src`, but every caller produces a Prop, so the `thmDecl` path is always taken. Not raised.
- `Mathlib/Tactic/CategoryTheory/Reassoc.lean` (attribute): passing `none` is correct because `inferType` of the constant is the declared type. But this leaves `type?` in `reassocExpr`/`reassocExpr'` with no `some` caller anywhere in Mathlib or MathlibTest. Suggested removing it, matching what the PR did for `elementwiseExpr` (finding 2, advisory).
- `Mathlib/Tactic/CategoryTheory/Elementwise.lean` `elementwiseExpr` / attribute / `elementwise_of%`: the type is now computed internally from `inferType pf`. Dropping the type hint is safe because `mkAppN pf fvars` infers to `type'` up to top-level annotations. `extractCatInstance` still receives `type'`. The docstring never mentioned `type`, so nothing is stale. No finding.
- `Mathlib/Tactic/CategoryTheory/ToApp.lean` (attribute): dropping `mkExpectedTypeHint` is safe. `toCatExpr` calls `inferType`, which gives `info.type` with fresh level mvars, as its doc requires. The two lines that instantiate fresh levels could become `mkConstWithFreshMVarLevels src`, but that would bypass the callback's argument. Too marginal to request.
- PR level: there is no description, and the `perf` claim has no benchmark. That is a process concern rather than something the code supports, so no finding was emitted.
