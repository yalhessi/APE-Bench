# How a convention earns a place in PR review

An incoming PR poses a design choice. The reviewer's job is to decide whether a change would help a Mathlib user enough to ask the author for it. For a bound on an infinite product, the revealing question is who can use it. A caller who already knows the product converges to a specified value may need a result about that value. A caller who only wants the total may be served by the theorem already in the PR. This choice gives us an observable unit smaller than “does this PR follow conventions?”

## What the harness should do

Keep the solo reviewer in charge of the whole PR. Use a convention to select one investigation with a concrete reason it might matter. The implementation can attach that investigation via the existing solo brief or per-PR context. The reviewer reads the diff, inspects the relevant existing interface and, when appropriate, tries the same small client against the submitted interface and a candidate alternative. The normal review submission remains the author-facing output.

Keep three records with different purposes:

| Record | What belongs there | What would count against it |
|---|---|---|
| The convention at a date | The choice, a narrower scope, the claimed benefit to a caller, supporting and contrary implementations, available tools and dated requests or explicit disagreements. Count distinct opportunities in comparable modules or families and identify shared source lineages. | A more general operation already serves the same caller. New independent implementations choose a different interface. An older example assumes an incompatible typeclass or import. |
| One opportunity in a PR | Base revision, changed declaration, trigger, the caller and premises, concrete evidence available at review time, and the remaining uncertainty. Record checks the system could not perform. | The declaration concerns an equality outside the order-bound scope, the supposed extra API already exists, or the client works with an equally direct existing operation. |
| The reviewer's decision | A short private record of the evidence inspected, the action considered and why it was requested or dropped, plus the exact submitted and retained finding when present. An author-facing request must identify the change. | Recommending an addition already in the source, repeating the cue without a caller, a failed technical check, or losing a justified request on the way to the final review. |

These can be study artifacts before they become new harness types. A reviewer's prose can identify a reason for a choice. The sealed prompt shows exposure, the tool trace shows inspection, and the final finding shows filing. When those disagree, retain each observation. Do not discard an ungrounded request merely because the finalizer gave it a low evidence grade, or count a private idea as author feedback.

## Learning scope and detecting change

Use three sources, all available before the PR's first review. A historical request can reveal why a maintainer wanted an edit, and an explicit later objection can reveal its limits. Merged declarations show which interfaces people actually implement and call. Tools answer specific technical questions: whether a client elaborates, whether an existing lemma closes the goal, or whether a linter fires in the PR's configuration. A compiling alternative establishes feasibility. Include alternative implementations and ordinary unchanged code when estimating how widespread the choice is.

Track opportunities and choices by module, mathematical assumptions, and time. Use incoming submissions for deployment coverage and merged code for library practice. Preserve author provenance, including AI-assisted contributions where identifiable, and retain PRs with zero recorded human asks for prospective comparison. Treat an unreviewed line or a silent maintainer as missing evidence of enforcement. Treat an explicit request, its uptake, and an explicit refusal as three distinct observations.

When new independent code takes a different course, check what changed at that snapshot: hypotheses or subdomain, available operations, or preference under the same conditions. A first use or linter release dates a capability. Subsequent adoption needs a denominator of new comparable choices, including the old choice; a file copied across dates is the same lineage. A deprecation, a replacement used by comparable new callers, or an explicit reviewer reversal can motivate reopening the convention. Record the last supporting and first contrary observations and the uncertainty between them. If the evidence is sparse or split, narrow the scope or suspend delivery pending new cases. ## What would establish improvement

1. **Establish that the opportunity can be found.** Freeze an input-only routing rule before examining outcomes. On a consecutive, previously unexamined sample, record every PR, every trigger and abstention, a random audit of non-firings, and independent scope labels. Measure coverage and routing errors. A known positive chosen by hand cannot answer this question.
2. **Show that the reviewer uses the premise correctly.** Pair the same incoming change with an edit that changes only the relevant fact. Ask for appropriate addition, reuse or silence. Count duplicate and technically false requests and retain the whole review. A dated irrelevant precedent or a length-matched generic inspection instruction can then separate benefit from the attention drawn to the area. Use these controls if the simpler comparison shows a gain.
3. **Test actual author benefit.** Freeze a fresh chronological PR cohort, convention evidence, solo baseline, tool access and token limits. Run both on every routed PR and evaluate the overall policy across all arrivals, weighting any sampled non-fires back to the sampling frame. Use the project's two existing primary outcomes: a delivered comment that identifies the expert's issue, and a delivered change that would satisfy the expert's request. Randomize display order and blind matchers to arm. Independently check additional or unmatched comments for demonstrable errors, duplicates and reading burden. A historical non-mention leaves worthiness unresolved; reserve maintainer adjudication for explicit decisions with an observable premise. Report other issues displaced, author comments per PR, tokens and latency. Compare paired PR-level differences with intervals clustered by PR or family, including PRs with no recovered issues. [Project evaluation decision](../../../../docs/research/project-assessment-2026-11-12.md)
4. **Specify the decision before running.** Treat the matched pilot as a mechanism check. For the next comparison agree with maintainers how many unwanted comments they will tolerate per additional useful one. Predeclare that benefit and burden criterion, sample across enough independent families to estimate it, and reserve an untouched time window. If routing rarely fires, measure another family before running a large model suite. If solo already finds the same issues, inspect errors unique to each arm before buying more repetitions. If a known source yields repeated redundant advice, reduce delivery or narrow the scope before collecting more positives.

This follows the previous studies' finding that offering a named convention can help when someone already knows the answer, while successful retrieval, applicability and usefulness each require distinct evidence. ## A second family with enough natural controls

Use the existing public-name retirement study for the next feasibility check. It already distinguished moved or generated declarations from disappearing names, observed 108 retirements with a deprecation and 32 without one, and identified 14 PRs where a missing-alias check would fire without a round-one comment. Start with those 14 for development adjudication, mixed with moves, existing aliases and aliases to the wrong successor. Include all 14 regardless of whether the decision looks obvious. The unanswered question is whether a reviewer can use evidence about a *real downstream compatibility cost* to improve the request it delivers over ordinary solo **and** over the deterministic check alone. An unobserved historical comment cannot label those 14.

For each candidate, test the old name at the old type before and after the patch, inspect whether the replacement preserves the API and which imports expose it, date the introduction of the old name, and inspect dated project guidance and comparable retirements. Where a compatibility alias works, a maintainer may still judge it unnecessary for a very recent or internal name. Where the old call already works through generated declarations, an “add the alias” comment is redundant. Have readers make that decision before seeing the model findings. Hold out later PRs for the comparison and use its results to decide whether maintaining this convention adds value beyond the compiler check.
