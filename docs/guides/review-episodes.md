# What we extract from a Mathlib PR

A PR number names a conversation whose code and description can change. A **review episode** identifies the occasion on which someone assesses a particular revision. A historical first-round case has two views of that occasion. The reviewer gets the proposed contribution as it stood then. A researcher can later reconstruct what maintainers requested and how the author responded. Several generated reviews can address the same episode.

The shared join key here is `leanprover-community/mathlib4:42184:round1:c5474cb4a68a515228b49225b38a2507264f91f7`. To reconstruct the **input**, follow `episode_id → (base_sha, reviewed_head_sha, diff)`. To reconstruct **what happened**, follow `episode_id → feedback_event_ids → source_key → raw comment`, then inspect replies and available subsequent heads. To reconstruct **what our reviewer said**, follow the run and accepted attempt to this episode’s ordered findings. One study can produce several submissions and several readings of the same revision.

The raw store retains PR metadata, commits, discussion and per-head compares. The episode builder projects those sources into reviewer-visible input, a separately stored round boundary and an index of source events. The index contains pointers and payload hashes. To read what an author actually wrote, follow the pointer to the raw record. Keep cohort metadata such as AI authorship identifiable when selecting cases. Its inclusion in a reviewer prompt is a separate design choice. **“After review” needs an endpoint.** The current first-round builder takes the earliest later commit timestamp as its proxy for the next push. The older v2 task’s near delta compares against the head at the *next maintainer event*, with a final-head fallback. These can span different edits. For an outcome analysis, record the two revisions actually compared, their merge bases and the patch evidence available. Where bases differ, use the change between the PR’s effective patches to avoid counting upstream churn as the author’s response. Preserve unavailable observations as such. Linking a subsequent change to a particular request requires evidence from the discussion or a stated interpretation. ## What a finding can be mapped to

| Research question | Representation and evidence |
|---|---|
| What did the reviewer ask? | Keep the accepted submission, its ordered findings, the original wording and any supplied location or edit. Identify a finding by its submission and ordinal. A completed empty list is an observed review. A missing submission is a run outcome. [Submission contract](../../src/ape/tasks/lean_tasks/formal_math/review/whole_pr.py) |
| Where did the reviewer point? | Preserve the original location. For source lookup use a revision, path, side and range where known. The existing change graph supplies changed ranges, entities on each side and change targets. A cited unchanged declaration can be looked up in the pinned tree even if it has no change target. Record which targets a resolver found, its method and any uncertainty. One location can support several requests. A missing location leaves scope unspecified unless the wording establishes a PR-wide concern. [Change graph schema](../../src/mathlib_review/schema/identity.py) · [Current anchor resolver](../../src/mathlib_review/review/candidates.py) |
| Which maintainer request did it address? | Compare the requested actions, with necessary thread context. A reading should be able to cite zero, one or several original findings for each request and record its judgment under the chosen rubric. Keep the inverse lookup too. On 34091 both matcher notes cite X1 findings 1 and 2 for the two docstrings in request `v0110`; the structured field records only 1. Conversely finding 5 is credited for three requests. The saved reach score counts `v0110` once. The missing information is the second supporting finding. [Original findings](../../results/pr_review_v5/probes/construction-demo-2026-09-29/pr34091/X1/findings.json) · [First reading](../../results/pr_review_v5/probes/construction-demo-2026-09-29/match/matches.1.json) · [Second reading](../../results/pr_review_v5/probes/construction-demo-2026-09-29/match/matches.2.json) |
| What happened to the historical request? | Link the historical request to a reply, later revision, specific edit or other observed outcome. Preserve the source and distinguish the observation from the conclusion drawn. The final tree can show adoption of an API shape. It cannot establish which advice the author followed or whether an unposted generated finding would have helped. [Outcome and judgment records](../../src/mathlib_review/schema/gold.py) |
| What did a specialist receive? | A work unit records a renderer-versioned group of same-file change targets. This is the right object for reconstructing what the specialist saw and for reproducing historical work-unit reports. [Work-unit builder](../../src/mathlib_review/release/work_units.py) |

**Design recommendation.** Keep the reviewed episode and the submitted finding as the two identities a whole-PR researcher follows. Attach source locations, matches to reference feedback, and evidence of subsequent author action as independently inspectable relations. Keep newly requested declarations in the finding’s text or proposed edit until a real revision contains them. Ordinary review should require no target classification from the reviewer.

Work units already existed in the v4 candidate generator (`32376791`). The v5 delegating reviewer adopted them as specialist assignments (`43e9d881`). The packing experiment makes their role concrete. I rebuilt work units over the same saved graphs using `build_work_units` and replayed the two guided 42184 findings through `anchor_submitted_findings`. With `candidate-prompt/11`, `/13` and `/14`, both findings resolved to the same change ID beginning `84eb374146`; the work-unit ID changed on every run. On 33145, the same twelve targets formed four units under `/11` and one under `/13`. Repacking should change the account of specialist work while leaving the PR, submission, source location and reading identifiable. **First implementation seam.** The current projector looks up the submitted start line on the reviewed side, resolves candidate change IDs, then picks the work unit of the first owned ID. Its output feeds historical candidate finalization. A comment spanning several lines currently enters that lookup through its first line. Original ranges belong with the submission. The prior walkthrough removed work units from whole-PR scheduling, but the run target still stores eligible work-unit IDs. To separate location from scheduling, let source resolution return its result before that lookup. The gold-side `ScopeResolution` already records the source cue, side, method, confidence and multiple change IDs. Reuse that vocabulary for source lookup while keeping historical interpretations on the evaluation side. Let the historical projector consume the lookup when it needs a work unit. The acceptance cases are a local request that locates the same declaration after repacking, the absent companion on 42184, the unlocated rationale on 41930, and the two-finding reading on 34091. Preserving a finding, locating code and crediting a request are three independently checkable results.
