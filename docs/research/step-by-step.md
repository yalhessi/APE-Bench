Project A is a good place to start, and your instinct to nail the task definition first is right. The one structural fact that should organize the whole plan: ground-truth review feedback only exists for human PRs. APE-Bench model outputs have no maintainer, so you can't evaluate them "with reviewing in mind" directly — you first have to build and validate the measurement instruments (task definition, stratum rubric, matchers, and ideally one or two verified checkers) on Mathlib's PR history, and only then point those instruments at APE-Bench outputs. The plan below follows that logic.

First, the candidate task definitions
Fix notation: a PR is (description d, base commit b, head h₀ = state when review was requested, giving diff δ₀). Round 1 feedback is the set of maintainer comments F₁ = {c₁…cₙ}; the author's response produces h₁, and Δ₁ = diff(h₀, h₁) attributed to feedback. The key representational move: gold for a review round is a set of (comment, resolving-edit) pairs {(cᵢ, eᵢ)} plus a verdict — the NL feedback and the diff changes you mentioned are two views of the same object, linked by which commits resolved which comments.

Three definitions, in increasing strength, all sharing input (d, δ₀, pinned workspace):

D1 — Verdict. Output: approve vs request-changes (+ confidence). Cheapest, but the label is one sample from a noisy process — report it, never headline it.
D2 — Findings (primary). Output: a set of findings, each with a location anchor, severity (blocking/advisory), stratum tag, and an NL claim. Gold: the actual round-1 comments. Evaluated by matched precision/recall and precision-at-comment-budget.
D3 — Revision specification. Output: the set of hunks/edits the PR needs before merge. Gold: feedback-attributed Δ₁ (or full Δ to merged head). This is the most objective definition — no comment-text matching, just "did you localize what actually had to change" — with merged-untouched hunks as the free false-positive control.
Restricting to the first review round is the simplification that makes this tractable: it matches exactly the inputs you listed, requires no conversation-context plumbing, and eliminates verdict/feedback leakage by construction. Later rounds can come back as an extension.

The step-by-step plan
Step 0 — Write the task spec (1–2 days). A short doc freezing D1–D3 contracts and the operational definitions everything downstream depends on: what event marks "review requested" (Mathlib has explicit process signals — awaiting-review/awaiting-author labels, bors r+, maintainer merge — use those rather than guessing from timestamps), who counts as a maintainer, and where round boundaries fall. Getting h₀ right is the single most error-prone choice; pin it to the head commit at the first maintainer review event.

Step 1 — Build the round-1 dataset slice (2–4 days). The collector in src/datasets/pr_review/ already pulls most of this; extend it to emit one record per PR: (d, b, h₀, F₁ with anchors, h₁, merged_head, label/bors timeline). Target ~150–300 merged PRs plus a batch of closed-unmerged ones, with the filtering funnel documented. Implement a first-pass comment→commit linkage (file/line overlap + temporal order + resolved-thread markers).

Step 2 — Hand-audit 30 PRs (1–2 days). Gate. Read 30 records end to end: is h₀ really the pre-review state? Does the linkage attribute edits to the right comments? How much rebase/merge noise pollutes Δ? Gate decision: if per-comment linkage is unreliable, drop D3's per-pair form and fall back to PR-level Δ (still sound, just coarser). Don't proceed on unaudited extraction — every downstream number inherits its errors.

Step 3 — Stratum rubric + classify ~200 comments (3–5 days). This is Project A's core. Draft the V1–V4 rubric with an operational test per stratum ("what computation would decide this claim?" — compiles/lints already → V1; checkable by search or speculative proof → V2; statable as a mechanical rule → V3; else V4). Classify ~200 round-1 comments by hand, also tagging blocking vs nit. Deliverables: the rubric, the stratum distribution, and the cross-tab of stratum × severity. Gate decision: the distribution picks your primary task definition — V2-heavy means D2+D3 with verification is the story; V4-heavy means the distributional-verdict framing (Project C) matters more than expected.

Step 4 — Freeze metrics (2–3 days). Build the finding↔comment matcher for D2, hand-validate it on ~50 pairs once, then freeze it. Define D3's hunk-overlap scoring with the merged-untouched FP control. Decide the noise-ceiling caveat for D1.

Step 5 — Baseline runs (≈1 week). Run plain Claude Code/Codex and 1–2 frontier models zero-shot on D2/D3 over the held-out slice. Purpose is not leaderboard numbers but instrument validation: does the task discriminate between models, and where do failures concentrate by stratum? This also surfaces the precision problem (expect heavy over-flagging) with real data.

Step 6 — Point the instruments at APE-Bench (the goal, ≈1–2 weeks). Take proof-engineering solutions from your APE-Bench reproduction that pass dual verification, and review them under the same task definition. Since there's no maintainer gold here, use the judge-independent instruments: the full lint suite, plus one or two V2 checkers worth building by then (duplication via exact?/Loogle is the cheapest; speculative generalization is the most striking), plus your own hand-review of a small stratified sample using the Step 3 rubric. The headline question: what is the stratum-tagged finding rate on verified-passing model outputs vs. matched human PRs at h₀? If verified APE-Bench solutions accumulate substantially more V1–V3 findings than human first-push PRs, you've quantified exactly what APE-Bench's evaluation misses — the "deeper evaluation with reviewing in mind" you're after, with no LLM judge in the loop.

Total: roughly 4–6 weeks to the APE-Bench result, with two cheap kill-switches (Steps 2 and 3) before any heavy investment. The biggest risks, in order: h₀/linkage extraction quality (audited at Step 2), rubric fuzziness between V2 and V3 (resolve by always asking "what would the checker be?"), and the temptation to skip Step 5 — don't, because if D2/D3 can't separate baseline models from each other, the APE-Bench comparison in Step 6 won't be interpretable either.
