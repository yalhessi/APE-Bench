# Which APE tools could run outside an APE session?

24 November 2026 · upstream `20017343` · Mathlib review fork `e9a048c3`

**The first public APE-Harness release let the benchmark change agents and keep the same Lean services. Running individual tools independently was possible, but some needed an adapter to supply what an APE task normally provided.** The April and May 2025 versions of the paper describe the earlier file-level benchmark and Eleanstic verifier. The February 2, 2026 revision describes the three-scaffold framework. The authors’ public `main` has one root commit dated February 3, which is also the root of this fork. That is the earliest implementation of the three adapters we could verify. [April paper][v1] · [May revision][v2] · [Scaffold design][design] · [Upstream commit][commit]

### Who supplies the workspace?

In a benchmark run, APE prepared the workspace and registered its tools. APE-Agent called them in process. The managed Claude Code and Codex batch adapters connected through MCP over HTTP. Each agent could then present the capability differently. In the authors’ proof-engineering experiments, an APE-Agent file edit could compile the change immediately. Claude Code and Codex issued a separate verification call. Even within one vendor, launch modes differed. The Codex batch adapter pointed its bridge at the generated MCP configuration. The interactive launcher started Codex with its usual configuration directory and did not explicitly select that file. [Reported comparison][comparison] · [APE-Agent][ape] · [Claude SDK][claude] · [Codex configuration][toml] · [Batch environment][env] · [Interactive launch][interactive] · [MCP registration][registration]

The authors’ standalone **declaration search** shows exactly where the inconvenience arose. An HTTP client could call `POST /lean-retrieve`. The endpoint and the MCP tool both called `lean_retrieve_impl`. A caller starting the server could specify the repository and commit, but behind that interface the factory constructed a `MockTask` and a scaffold configuration named `lean_retrieve_test`. The client escaped the APE task lifecycle because someone had already written that adapter. [HTTP service][http] · [MCP retrieval][retrieve] · [Provider factory][factory]

The original **Lean verification engine** had a simpler Python interface. We exported the upstream source and called `VerificationEngine().verify(code, working_dir=project)` on a temporary Lean 4.24.0 project. With no task or agent running, `example : 2 + 2 = 4 := rfl` passed and changing the right-hand side to `5` produced a type mismatch. The model-facing `lean_verify` provider added workspace rules and read tool settings from the scaffold configuration before it called that engine. [Verification engine][verification] · [Tool provider][provider]

**Submitting a result** has a genuine dependency on a running task. In the upstream proof-engineering task, `submit_result` evaluated the code and signaled completion when the stopping condition was met. In the fork, `submit_findings` checks the review budget and records the PR result. A reusable declaration lookup can serve many callers, while a submission needs an identified recipient and rules for what counts as complete. [Original submission][submit] · [Review submission](../../src/ape/tasks/lean_tasks/formal_math/review/base.py#L699)

### What changed in the fork?

On September 25 the fork exposed its review tools to independent probes through `cli tool`. It reused the implementations by constructing a stand-in review task. On PR 30458 the probe used the PR’s source files with the base commit’s compiled dependencies. One changed file used a declaration generalized in another. Lean reported two missing `Group` instances in a file that compiled in the reviewed workspace. The September 29 fix made the probe use the same reviewed-workspace setup as the task. This is the practical reason to share the workspace resolver as well as the tool function. An external agent should be able to name the PR once and rely on that resolver for subsequent checks. [Toolbox history](../../src/mathlib_review/review/toolbox.py#L14) · [Regression case](../../tests/datasets/test_pr_review_v5_toolbox.py#L57)

### What does extracting the review operations buy us?

A researcher should be able to open Claude Code or Codex, select a PR and use the same Mathlib tools that an APE benchmark run would grant. Bind the reviewed revision, source view, historical cutoff and target-PR exclusion once. Let each operation acquire its actual dependencies. A Zulip lookup needs a dated corpus. Checking an edit needs the appropriate Lean project. Keep the research logic that chooses what to investigate and what to file with the reviewer. For a cohort run, APE can still supply the cases, collect the ordered submissions, retry failures and score the reviews. [Proposed interfaces](../plans/2026-10-22-review-operations-foundation.md#2-architecture-and-data-handoffs) · [Existing run and import paths](../../src/mathlib_review/analysis/sessions.py#L10)

#### Connecting an independently started agent

With a temporary stdio launcher around the branch's `open_workbench(...).mcp`, we granted only `base_source_read` on PR 33098. Using isolated temporary client settings, Claude Code 2.1.331 reported a connected server. Codex CLI 0.172.0's app server listed exactly that tool and used it to read three lines of `Mathlib/Topology/MetricSpace/CoveringNumbers.lean` at base `af239326a46dea977a6d5444466c14aa423f4b10`. The Codex request directly invoked the tool; no model selected it. This verifies the client connection and one scoped operation. The proposed implementation work is to integrate the shared operations and ship and maintain the launcher used for that workflow. A session that only wants to investigate a PR can stop there. A benchmark session additionally needs somewhere to submit its answer. [Workbench](../../.claude/worktrees/review-operations/src/mathlib_review/review/toolbox.py#L155) · [Standalone launcher in the plan](../plans/2026-10-22-review-operations-foundation.md#L201)

#### What might change in an actual review?

**A reviewer filed a previously missed maintainer request after gaining compiler access.** On PR 26308, a reviewer with source search alone examined `normalized_smul_of_pos` and explicitly left it out because it could not check a shorter proof. A second reviewer with the same brief compiled a one-line `simp` replacement and submitted it as finding 5 (zero-based). Both blind matchers scored the maintainer’s request `v0189` as missed in the first review and reached in the second. They also scored a different proof request, `v0188`, as reached in the first and partial in the second. Both matchers credited each reviewer with five requests on this PR. These were independent sessions, one per condition, and the toolbox added several tools together. This case shows why a probe wanted the compiler. The September CLI already delivered it. **A second kind of task used the extracted operations.** On the unmerged `knowledge-transfer@1474776d`, APE-Agent and managed Claude Code each ran a preparation session on PR 33117 with eight review tools. Both found two occurrences of `lemma fun_add` in the base source and compiled the submitted file. Both also reported the same missing declaration table for `proof_profile`. Supplying that table made the operation succeed on the two pilot bases. [APE-Agent output](../../.claude/worktrees/knowledge-transfer/results/pr_review_v5/probes/knowledge-transfer-2026-10-23/recipe/smoke/plan/outputs/task-kt_smoke_ape/pr33117/1/smoke.md) · [Claude Code output](../../.claude/worktrees/knowledge-transfer/results/pr_review_v5/probes/knowledge-transfer-2026-10-23/recipe/smoke/plan/outputs/task-kt_smoke_claude/pr33117/1/smoke.md) · [Resource repair](../../.claude/worktrees/knowledge-transfer/results/pr_review_v5/probes/knowledge-transfer-2026-10-23/recipe/smoke/RESULTS.md) · [Launcher decision](../plans/2026-10-22-review-operations-foundation.md#L201)

**The measured review outcome still depended on how the reviewer used the evidence.** On PR 36784 a preparer found that sibling rules were `safe` and the new rule matched only the coercion from units. It used those facts to argue that the rule belonged in the default rule set. The maintainer had asked whether Aesop could apply it as a `safe` rule. Across the two pilot PRs, each repetition of ordinary and conditional preparation led to final reviews reaching the same one of four historical requests. Both conditions had the shared tools. The pilot tests the preparation method and leaves the effect of an independent launcher on review quality unmeasured.
