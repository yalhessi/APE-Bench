# An author-facing first review for Mathlib

**Research direction, 23 November 2026.** Build one reviewer that can read an incoming Mathlib pull request and give its author the feedback a maintainer would otherwise have to write. The unit of work is a contribution. It can be a new formalization, a small proof edit, a documentation correction, a rename, a cross-library migration or a tooling change. An actionable review can consist of a checked edit, a reason to rethink the change, a precise question, or no comment. An API decision is one case in this workload.

**Working hypothesis.** Earlier expert reviews can teach an agent *which changes to ask this contributor to make*. Train a small proposal model on the submitted change and the actual first-round requests from earlier PRs. Let the strongest existing whole-PR reviewer investigate those proposals, raise issues of its own, and compose one review for the author. I predict that, for the same amount of feedback to read, more of the work experts would ask for will reach the author than with the generalist alone. The prediction applies across materially different kinds of PR. This takes up November's proposal to learn from expert requests. [Earlier proposal](review-harness-design-alternatives-2026-11-12.md)

## What the broader evidence says

The large development audit contains **973 PRs and 1,833 expert requests**. Proof feedback accounts for **22.1%**, statement and API design **14.3%**, documentation **12.4%**, formatting **11.8%** and naming **9.7%**. Whole-PR questions account for **16.1%** of requests on flagged AI contributions and **5.1%** on the others. A single PR adding a theorem can draw several of these categories of feedback. The sample includes an oversampled AI stratum and the existing release's size and content filters. [Audit, denominators and codebook](pipeline-overfit-2026-09-replication.md)

## The contributor's first pass

1. **Start from whatever the contributor submitted.** Give the reviewer the review-time diff, the verified description and title when available, and access to the repository at that revision. For a large PR it can open relevant files and follow dependencies while retaining the PR-wide objective. A docs or workflow review should be able to finish without a Lean tool call.
2. **Use historical reviews to generate candidate feedback.** Train a compact instruction model with a lightweight adapter to draft open-text, located or PR-wide requests from whole PRs. A training target is the set of requests human reviewers actually wrote about that revision. Preserve related comments and questions. Posting order reflects the course of the discussion. The targets therefore teach candidate content, with priority and omission left to the final reviewer. A new diff goes in without a reviewer-marked location or proposed alternative. The model can suggest a missing explanation, a proof experiment, the removal of a duplicate, a migration step or a scope change using the same output format.
3. **Let one generalist investigate and write the review.** Its starting material is the PR, its own open review and the draft requests. It checks a proof in Lean, a rename against actual uses, a factual documentation claim against its source, or a CI claim against the workflow as appropriate. It asks a precise question when the author has information the repository cannot supply. It puts a blocking issue first and groups comments that the same revision would settle. A request to replace a whole contribution gives it a concrete reason to drop line edits that would disappear. It can return an empty review. There is no per-category quota.

The author would receive the first review before a maintainer picks up the PR. Give an edit at the affected lines when possible and explain project-wide changes or questions once at the PR level. For example, earlier expert reviews asked an author to explain the benefit of a technically acceptable change, and asked another to separate proof edits using the `grind` tactic from edits the maintainer said they could review faster. The first example gives the system a reason to ask for motivation on a future rename. The second gives it a specific way to make a mixed PR easier to review. Whether training transfers either action to the right new PR is the empirical question. [Request for motivation](https://github.com/leanprover-community/mathlib4/pull/27299#issuecomment-3093423930) · [Request to split the tactic changes](https://github.com/leanprover-community/mathlib4/pull/28872#pullrequestreview-3149500637)

This uses history during training to alter the questions the agent investigates. July's code-similarity priming, October's convention banks and a late filter over already generated findings tested different approaches. The best verified solo route is the baseline. The old ten-specialist run attributed **64 of 71** development hits to its generalist, and the generic pointwise selectors were weak. Simply adding passes or rearranging a long list has little support. All three of the questions targeted by the full historical bank were missed even though its total match count rose. [Solo and specialist record](../questions.md) · [Selector test](selector-upper-bound-2026-06.md) · [Historical bank results][bank-matches]

There is also evidence that the task an agent takes on affects what it catches. On ten PRs selected for multiple PR-level asks, the September prompt focusing on the whole contribution reached 12 or 11 of 21 requests in **both** repetitions, according to the two matchers. The ordinary brief reached 9 or 6 in its one run. The focused reports averaged 5.2 findings per PR and missed the study's volume target. Prior work has therefore already tested telling the agent to attend to PR-wide matters, and demonstrated both a benefit and a cost. [Focused-brief runs](facet-brief-probe-2026-09.md)

### A source corpus that exists now

I paired **390 distinct reviewed PRs** with **1,140 first-round requests** both census readers identified as asks, using rounds whose recorded feedback all preceded **1 January 2026 UTC**. Of the requests, **141** occur in top-level reviews or PR conversation, outside inline code comments. There are **37** PRs with AI authorship evidence in this source subset. The export verifies each reviewed snapshot and the event IDs against its original review boundary. Every diff matches its stored SHA-256. The model-facing input contains the review-time diff and description. Human-selected locations and comment text are on the target side. Unverified titles are omitted. [Source pairs](../../data/pr_review_v5/first_round_development_before_2026-01-01.jsonl) · [Reproducible export](../../results/pr_review_v5/adjudications/arm-coverage-val1000-2025-06-2026-03-v1/provenance/first_round_examples.py)

This is positive supervision drawn from the previously studied 973-PR development census. There are 148 source PRs without a nonempty recoverable description, two comparisons with an unavailable textual patch for at least one file, and 55 request events that are inline replies. For a first-pass training objective, supply only previously visible discussion as input or omit targets that need an unseen reply. Include later quiet reviews and explicit approvals when measuring whether the system creates unnecessary work. Assess their outputs directly because historical silence has many causes. The corpus supports a small pilot. Its size and historical mix may be insufficient to improve a frontier reviewer.

## Relation to prior work

CodeReviewer already learns comment generation and code refinement from historical code reviews. SWE-PRBench already evaluates generated reviews against human PR feedback, and Asada and colleagues already measure reuse of extracted historical rules. The paper would need to establish whether learning from *whole Mathlib contributions and their expert requests* improves what contributors receive from a tool-using generalist at a realistic reading budget, including failure regimes outside conventional Lean proofs. Training an adapter alone is an implementation choice. ## What the comparison experiments tell us

The rationale for supplying two feasible designs was experimental control. Holding the alternatives fixed lets us ask whether an earlier expert decision changes the model’s preference. The focused generality case motivated that question because the model could already construct the change. That observation identifies a disagreement after construction. It gives us no estimate of how often ordinary reviewers reach that point or how often an example would resolve the disagreement. An earlier reviewer’s observation that a proof’s use of square roots needlessly restricted an inequality, for instance, does not decide whether the constant in a different theorem merits generalizing. [Historical discussion][generality-source] · [Focused answers][focused-answers]

### Reproducing the source availability count

Run this read-only check from the repository root with the local data store. It uses the original bank selection at `bbba4f24`, the three types of same-PR GitHub discussion items, and the original acquisition cutoff. It measures record availability before ranking. The API examples use local Lean replays. The reading-budget counts use the two saved matcher readings and the finalized findings from the original reviewer runs.

```python
import json
import subprocess
from collections import Counter
from pathlib import Path

selection_path = "results/pr_review_v5/probes/reusable-review-knowledge-2026-10-24/selection.json"
selection = json.loads(subprocess.check_output(["git", "show", f"bbba4f24:{selection_path}"]))
cases = [c for e in selection["entries"] for c in e["cases"] if c["role"] == "induction"]
source_prs = {case["pr"] for case in cases}
cutoff = selection["K"]
indexed = set()
with Path("data/pr_review_v5/precedent_index/meta.jsonl").open() as rows:
    for line in rows:
        row = json.loads(line)
        if row["pr_number"] in source_prs and row["created_at"] < cutoff:
            indexed.add((row["pr_number"], row["comment_id"]))

totals = Counter()
for case in cases:
    pr = case["pr"]
    cited = 0
    found = 0
    for endpoint in ("review_comments", "reviews", "issue_comments"):
        ids = set(case["comment_ids"].get(endpoint, []))
        if not ids:
            continue
        with (Path("data/pull_requests/pr") / str(pr) / f"{endpoint}.jsonl").open() as lines:
            rows = (json.loads(line) for line in lines)
            records = {row["id"]: row for row in rows if row["id"] in ids}
        assert ids == records.keys()
        assert all((r.get("submitted_at") or r["created_at"]) < cutoff for r in records.values())
        totals[endpoint] += len(ids)
        cited += len(ids)
        if endpoint == "review_comments":
            found += sum((pr, event_id) in indexed for event_id in ids)
    totals.update(cases=1, indexed=found, any_present=int(found > 0), all_present=int(found == cited))
print(totals)
```
