# An author-facing first review for Mathlib

**Research direction, revised 24 November 2026.** Build one reviewer that can read an incoming Mathlib pull request and give its author the feedback a maintainer would otherwise have to write. The unit of work is a contribution. It can be a new formalization, a small proof edit, a documentation correction, a rename, a cross-library migration or a tooling change. An actionable review can consist of a checked edit, a reason to rethink the change, a precise question, or no comment. An API decision is one case in this workload.

**Working hypothesis.** Expert review includes knowing what evidence would justify making, narrowing or dropping a request. Train the policy that writes the review to *act on that evidence*. Use historical discussions where the PR author supplies a fact or a counterexample and the requesting reviewer explicitly responds. The source of supervision is the link from a particular reason to the action the reviewer then takes. At first review the agent has just the submitted PR and the repository. It can check a premise itself or ask the contributor a question that would change its advice. The prediction is better first-pass feedback on different kinds of PR at a comparable reading burden. Learning to draft more plausible requests from initial comments, November's alternative 3, is a baseline for this claim. [Earlier proposal](review-harness-design-alternatives-2026-11-12.md)

## The contributor's first pass

1. **Start with the submitted PR.** Use the generalist and its existing review tools across proofs, library design, docs, small fixes, migrations and CI. It can raise an issue itself, put one blocking request ahead of local comments, or finish with no request.
2. **Teach the reviewer what to check before it commits to a request.** For an older discussion, hide the author's answer and the reviewer's follow-up. Have the learner investigate the submitted change and draft what it would ask. For supervision, use a check justified by the actual exchange whose result can be reproduced at that revision, such as opening the CI consumer. If the decisive fact was known only to the author, retain an actual clarifying question where the discussion supplies one. Exclude cases with ambiguous justification from this training target. The check reconstructed by the study is a derived target. The recorded human request and follow-up remain separate observations.
3. **Update the component that sends the advice.** Where the original reviewer explicitly maintains, narrows, changes or withdraws the request, use that reply as a second target conditional on the visible discussion. Use the verified checks and actual follow-ups as supervised targets for a trainable reviewer, with an adapter as a modest implementation. Its own first attempt exposes whether it missed the condition or considered it and took the other action. Measure both. An upheld request is as important a training case as a withdrawn one. At run time that policy can revise its own initial draft after a tool result or an actual author reply. Group training and evaluation examples by PR and linked change series. Count a wrong mandatory edit, a justified question and an explicitly withdrawn request according to their distinct consequences for the contributor.

Earlier work tested dated examples, reasons, contrary cases, explicit investigation, priority instructions, enforced filing, and critics of existing findings. The September whole-PR prompt improved some PR-wide decisions at higher volume. These are precedents for individual parts of this design. The proposed difference is to update the decision-making policy against the actual expert's response to new evidence and test transfer back to independent first reviews. A learner that merely repeats the final wording after seeing an author's answer has passed a dialogue task. The substantive claim requires it to identify and investigate the decisive fact on a new PR by itself. [Knowledge-transfer synthesis](knowledge-transfer-experiment-synthesis-2026-10-23.md) · [Filing studies](../questions.md#the-filing-decision) · [Historical bank results][bank-matches]

On ten PRs selected for multiple PR-level requests, the September prompt focusing on the whole contribution reached 12 or 11 of 21 requests in both repetitions, according to the two matchers. The ordinary brief reached 9 or 6 in its one run. The focused reports averaged 5.2 findings per PR and missed the study's volume target. Preserve ordinary review as the common starting point and compare the final reviews at the same reading budget. [Focused-brief runs](facet-brief-probe-2026-09.md)

## What the comparison experiments tell us

The rationale for supplying two feasible designs was experimental control. Holding the alternatives fixed lets us ask whether an earlier expert decision changes the model’s preference. The focused generality case motivated that question because the model could already construct the change. That observation identifies a disagreement after construction. It gives us no estimate of how often ordinary reviewers reach that point or how often an example would resolve the disagreement. An earlier reviewer’s observation that a proof’s use of square roots needlessly restricted an inequality, for instance, does not decide whether the constant in a different theorem merits generalizing. ### Reproducing the source availability count

Run this read-only check from the repository root with the local data store. It uses the original bank selection at `bbba4f24`, the three types of same-PR GitHub discussion items, and the original acquisition cutoff. It measures record availability before ranking. The API examples use local Lean replays. The reading-budget counts use the two saved matcher readings and the finalized findings from the original reviewer runs.

```python
import json
import subprocess
from collections import Counter
from pathlib import Path

selection_path = "results/pr_review_v5/probes/reusable-review-knowledge-2026-10-24/selection.json"
selection = json.loads(subprocess.check_output(["git", "show", f"bbba4f24:{selection_path}"]))
cases = [c for e in selection["entries"] for c in e["cases"] if c["role"] == "induction"]
source_prs = {case["pr"] for case in cases}
cutoff = selection["K"]
indexed = set()
with Path("data/pr_review_v5/precedent_index/meta.jsonl").open() as rows:
    for line in rows:
        row = json.loads(line)
        if row["pr_number"] in source_prs and row["created_at"] < cutoff:
            indexed.add((row["pr_number"], row["comment_id"]))

totals = Counter()
for case in cases:
    pr = case["pr"]
    cited = 0
    found = 0
    for endpoint in ("review_comments", "reviews", "issue_comments"):
        ids = set(case["comment_ids"].get(endpoint, []))
        if not ids:
            continue
        with (Path("data/pull_requests/pr") / str(pr) / f"{endpoint}.jsonl").open() as lines:
            rows = (json.loads(line) for line in lines)
            records = {row["id"]: row for row in rows if row["id"] in ids}
        assert ids == records.keys()
        assert all((r.get("submitted_at") or r["created_at"]) < cutoff for r in records.values())
        totals[endpoint] += len(ids)
        cited += len(ids)
        if endpoint == "review_comments":
            found += sum((pr, event_id) in indexed for event_id in ids)
    totals.update(cases=1, indexed=found, any_present=int(found > 0), all_present=int(found == cited))
print(totals)
```
