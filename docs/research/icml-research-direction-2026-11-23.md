# Can an earlier expert review change a model’s next design decision?

**Research assessment, 23 November 2026.** I would spend the next six weeks on a controlled study of how reviewers use precedent when two technically plausible choices are available. The first question is whether seeing *what an expert chose in an earlier case* improves the model’s recommendation on a different PR. The second is how much of that effect survives when the reviewer has to find the choice and the precedent itself. Mathlib gives us an unusually good way to tell these apart. Lean can check many of the proposed edits, and the review thread records which edit a maintainer actually requested, qualified, or declined.

The project has evidence for responsiveness to relevant information. It still needs independent evidence of transfer of judgement. That distinction is large enough to frame a paper and narrow enough to test. I would target ICML 2027, use **4 January** as the internal decision on the evidence and full draft, and keep the remaining time for criticism and revision. The official dates are **14 January 2027** for the abstract and **22 January** for the eight-page paper, both at 11:59 p.m. Anywhere on Earth. The ICLR 2027 and AAAI-27 main-paper deadlines passed in September and July respectively. ## The experiment worth buying

**Use history at the moment a reviewer has to choose.** Keep one short record of a live choice. Record the submitted design, one feasible alternative, and the fact that would change the recommendation. Retrieve one or two earlier review discussions from that question and the visible code. Return the source code before review, the expert’s action, and any stated reason or explicit qualification, with author, date, and scope. Attribute an author’s objection separately from a maintainer’s agreement. Keep the action when the reason is missing. The reviewer identifies the source–target correspondence, checks the most important difference using the reviewed library where possible, and can recommend a change, keep the submitted form, or say the evidence is insufficient. In whole-PR review the author sees ordinary actionable feedback.

For example, an earlier Mathlib reviewer identified a restriction to real numbers that came from using a square root in the proof of an inequality. That example suggests asking whether a restriction comes from the mathematics or the proof. It does not settle whether a new theorem should be generalized. On PR 33421 the proposed general theorem can recover the old case. On PR 33000 a proposed derivation would have required extra hypotheses, including characteristic zero, that the existing derivative result did not need. The suggester agreed to preserve the existing result. A system that says “generalize” on both cases can look good on an ordinary count of positive requests. Both threads are already known, so they illustrate the experiment and cannot validate it. [Earlier inequality discussion][generality-source] · [Two target decisions][selection-note]

**First isolate whether the expert decision adds information.** On development material, assemble a small panel of real decisions from at least two recurring families, starting with theorem generality and automation registration. Seek both explicit requests and explicit decisions to retain or qualify an alternative. A proposed first-week target is 12 distinct PRs across the two families and both directions, enough to exercise the design. Report the search denominator, ambiguous or unsupported threads, and their exclusions. A separate input builder prepares the target site and plausible options using only the pre-review snapshot. Keep a count of how often those options contain the expert’s eventual choice. If a site or option has to be supplied from the expert thread, label the comparison conditional on that cue.

Use the same target, options, earlier source IDs, order of excerpts, model, tools and budget ceilings in four short conditions. Randomize option order across cases, independently of the expert’s choice. Use fresh sessions.

| What comes from each source | Ordinary decision prompt | Prompt asking which source fact carries over and which difference could reverse the choice |
|---|---|---|
| Pre-review source code and context, with the source decision hidden | Base comparison | Tests the comparison procedure alone |
| Same pre-review source plus the actual expert action and any stated grounds | Simple example delivery | Tests deliberate use of the same evidence |

Remove cues to the *source* decision from its code-only packet, including titles and later edits. Withhold the *target* discussion from every arm. Preserve the target’s technical information and match token allowances, then record actual use. Choose source IDs using a frozen search on the visible target, independently of its reference. A separate diagnostic with an investigator-supplied relevant source can show what happens when retrieval succeeds. If the expert text helps, repeat a subset with genuine, similarly long, same-topic discussions reassigned across cases within the date cutoff. An equally large gain from reassigned discussions would weaken the attribution to the particular precedent.

Better decisions with the historical text under either prompt support an information effect. A further gain from explicit comparison with the *same* sources supports that delivery procedure, especially if the comparison prompt alone buys little. More change requests even on cases where experts explicitly declined the analogous change indicate a shift in willingness to ask. Score requests and explicit retentions separately, count abstentions, and include a training-only family-majority or always-request baseline. A request and a subsequent decision to withdraw it are distinct reference events. If a later decision depended on newly revealed information unavailable at review time, keep it out of the pre-review decision endpoint.

The supply of explicit contrary decisions is a practical risk. A previous reading of 154 relevant requests about using a library mechanism or a local implementation found only five with stated grounds on the local side. A balanced panel would test discrimination conditional on a documented choice. It would say little about the frequency of these choices in everyday reviews. If distinct contrary cases prove too scarce, narrow the claim to recovery of explicit requests and drop the claim about when to refrain. [Corpus reading](../../.claude/worktrees/grounds-reading/docs/research/library-mechanism-grounds-2026-10-22.md)

**Then test autonomous review once.** If a delivery method earns an independent test, run a resource-matched pair on the same fresh PRs. Use the strongest available reproducible solo route, with the same reviewed head, ability to reconsider, tool grants, and comment and token budgets. In treatment, let the reviewer produce open choices itself, including designs it provisionally intended to keep, then query the gated history and apply the winning method. Log how many historical issues never got a candidate choice, never received a relevant source, received one but got a different remedy, or appeared in the investigation and vanished from the final review. Count recovered issues outside the historical procedure too. The whole-PR contrast estimates the combined system effect. The shorter four-condition study identifies what the history and its presentation contributed. If simple delivery ties explicit comparison within the measured precision, prefer the simpler system.

**Judge what reached the author.** On whole reviews the primary outcome should be recovery of the expert’s requested resolution in the *finalized* output. Also report recovery of the specific issue, remedy disagreements, and coverage of explicitly linked sibling sites. Use naturally occurring expert requests as the reference. Additional unmatched findings have unknown value. Report them as reading burden along with total comments, tokens, and baseline recoveries lost. Compare paired PRs, show both matcher readings and individual PR gains and losses, and cluster uncertainty by PR. Keep PRs with no recorded request in the burden denominator. On the focused test report agreement by direction and family. Here “calibration” means improvement in these observed decisions. A probability-calibration claim would require a separate probability target. [Atomic judge](../../src/mathlib_review/judge/protocol.py) · [Request matcher](../../src/mathlib_review/judge/ask_matching.py)

For scale, suppose the short test has one binary decision per independent PR and two conditions disagree on a quarter of cases. Near zero effect, the approximate 95% half-width on the paired difference is 20 percentage points for 24 PRs and 13 for 60, from `1.96 × sqrt(0.25 / N)`. Those are planning examples. Use the observed validation discordance to decide how much precision the budget buys. A small null with a wide interval should leave the question open.

## What would justify an ICML paper

Other groups already retrieve review examples, summarize project rules, and evaluate AI reviews against human feedback. RAG-Reviewer retrieves code–comment exemplars, LAURA adds context and review guidance, and SWE-PRBench measures recovery of human-flagged issues. Atlassian has compared historical comments and diffs directly. A particularly close November 19 preprint by Asada and colleagues compares an unedited source thread with an extracted rule on 20 constructed changes and tracks which rules resulted in production comments. A rule-versus-thread ablation or a count of cited precedents would have substantial overlap. [RAG-Reviewer](https://arxiv.org/abs/2506.11591) · [LAURA](https://arxiv.org/abs/2512.01356) · [SWE-PRBench](https://arxiv.org/abs/2603.26130) · [Atlassian’s comparison](https://www.atlassian.com/blog/development/improving-code-reviewer-with-pr-context) · [Asada et al.](https://arxiv.org/abs/2611.25918)

MathlibPR predicts merge outcomes and audits some explanations. ProofJudge scores declaration quality and compares initial and accepted versions. Our opportunity is to test whether *the decision inside a historical example* changes the recommendation on a naturally occurring later choice, including cases where experts went the other way, and to measure the loss when the model must discover that choice unaided. This also connects to work showing that demonstrations can help even when their labels carry little information. Holding the code and target options fixed makes expert decision content experimentally distinguishable from a cue about the topic. Mathlib is the setting in which feasibility can be checked and the preference traced. Claims about other communities would require data from them. [MathlibPR](https://arxiv.org/abs/2605.07147) · [ProofJudge](https://arxiv.org/abs/2608.20432) · [Min et al. on demonstrations](https://aclanthology.org/2022.emnlp-main.759/)

- **A methods paper** becomes credible if correctly dated expert decisions improve both the focused comparison and final expert-resolution recovery on independent PRs at a comparable budget. Show the gains across cases, losses, and any concentration by author, family, or period. A second model on the cheaper decision task would help establish how model-specific the mechanism is.
- **An empirical evaluation paper** is credible if the controlled result replicates across independent decisions but transfer breaks at an identifiable stage, or if sufficiently precise comparisons bound a practically meaningful effect. Its contribution would be the decision dataset, the controlled comparisons, and evidence of where transfer breaks. ICML explicitly recognizes evaluations and informative negative results. [Contribution types](https://icml.cc/Conferences/2027/ContributionTypes)
- **Defer the submission** if the evidence still consists of the six familiar PRs, the earlier oracle, or a fresh comparison too imprecise to distinguish worthwhile gains from losses. A run of unsuccessful harnesses alone gives the reader little basis to choose a better approach.

### Reproducing the source availability count

Run this read-only check from the repository root with the local data store. It uses the original bank selection at `bbba4f24`, the three types of same-PR GitHub discussion items, and the original acquisition cutoff. It measures record availability before ranking. The outcome counts above use the two saved matcher readings and the finalized findings. This assessment introduced no new reviewer runs or semantic labels.

```python
import json
import subprocess
from collections import Counter
from pathlib import Path

selection_path = "results/pr_review_v5/probes/reusable-review-knowledge-2026-10-24/selection.json"
selection = json.loads(subprocess.check_output(["git", "show", f"bbba4f24:{selection_path}"]))
cases = [c for e in selection["entries"] for c in e["cases"] if c["role"] == "induction"]
source_prs = {case["pr"] for case in cases}
cutoff = selection["K"]
indexed = set()
with Path("data/pr_review_v5/precedent_index/meta.jsonl").open() as rows:
    for line in rows:
        row = json.loads(line)
        if row["pr_number"] in source_prs and row["created_at"] < cutoff:
            indexed.add((row["pr_number"], row["comment_id"]))

totals = Counter()
for case in cases:
    pr = case["pr"]
    cited = 0
    found = 0
    for endpoint in ("review_comments", "reviews", "issue_comments"):
        ids = set(case["comment_ids"].get(endpoint, []))
        if not ids:
            continue
        with (Path("data/pull_requests/pr") / str(pr) / f"{endpoint}.jsonl").open() as lines:
            rows = (json.loads(line) for line in lines)
            records = {row["id"]: row for row in rows if row["id"] in ids}
        assert ids == records.keys()
        assert all((r.get("submitted_at") or r["created_at"]) < cutoff for r in records.values())
        totals[endpoint] += len(ids)
        cited += len(ids)
        if endpoint == "review_comments":
            found += sum((pr, event_id) in indexed for event_id in ids)
    totals.update(cases=1, indexed=found, any_present=int(found > 0), all_present=int(found == cited))
print(totals)
```
