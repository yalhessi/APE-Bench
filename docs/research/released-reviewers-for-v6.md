# What four released reviewers hand to the next consumer

25 November 2026. APE-Bench at `35e6865e`.

**Proposed starting point.** Let a researcher run one reviewer on one frozen episode, obtain a reference to its accepted submission, and read that submission again under a different rubric. The smallest implementation has two public operations, `run` and `score`. The reason to save the review at that boundary is observable on Mathlib PR 42184. For example, `python -m pr_agent.cli --diff-file changes.diff --output review.md --json-output review.json review` requests both artifacts. The reviewer deep-copies the parsed review for structured consumers, adds usage and file-coverage data, then prepares inline issues and Markdown. ## How released systems actually conduct a review

Mozilla's generation prompt can include a patch summary, external context, similar human comments and approved generated examples. In experiment mode it passes the patch creation time to the example lookups. The service can then filter suggestions and add a separately generated request about the scope of the patch. Those are substantive choices about what reaches the author. For Mathlib, the transferable idea is a named reviewer with a dated source of examples and a record of what was supplied. Test that choice against solo on the same episodes. The service also has a separate matching tool that returns pairs of old and new comment IDs. Its rubric asks about redundancy on the same issue. PR 30641 shows why APE needs a rubric that reads the requested action too. Trying an existing tactic and registering a new lemma for it lead the contributor to do different work. Anthropic's released Claude Code plugin scopes a PR, finds applicable repository instructions, summarizes the change, assigns four independent reviewers, and validates flagged issues before returning a review. It can publish separately. Reading the correct repository instructions and recording what was visible transfer to a Mathlib strategy. Requiring every candidate to meet the plugin's bug or explicit instruction threshold would change the task: a maintainer can reasonably request a different API for a theorem that compiles. The Mathlib fanout test also recovered two of ten obligations on its four PRs, against four for solo. The implementations and populations differ. That local result makes fanout an experimental choice. GitHub's review thread representation supplies a historical identity for discussion across revisions. The platform exposes reply relationships, original and current locations, and thread resolution. Preserve event and revision identities at extraction. Count a maintainer request under a stated interpretation of the thread. A resolved flag or an empty later diff alone cannot tell a reader which response satisfied a particular request.
