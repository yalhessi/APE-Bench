# Implementation audit of the Mathlib PR review harness

24 November 2026 · `develop` at `235bc9f8`

The [comparison with other review harnesses](pr-review-harness-refactor-comparison-2026-11-24.md) extends this audit with a census of recoverable submissions, external design precedents and acceptance cases for the refactor.

The target is an author-facing first review of an incoming Mathlib contribution. Success means delivering the feedback an expert would ask the author to act on, in an order and volume the author can use. The current harness can run a whole-PR reviewer, but much of its downstream code still expects a specialist to report a candidate against a work unit. That difference changes both what survives and what the experiment measures. [Project objective and reading-depth evidence](icml-research-direction-2026-11-23.md#what-fits-in-a-review-people-might-actually-read)

**First investment.** Replay a dated PR snapshot and a saved submission through to the exact comments delivered and scored. There are demonstrated defects on both sides of that boundary. Fixing them gives every reviewer design a more reliable comparison. A new proposal source or delegation policy can then change how a reviewer investigates a PR while using the same submission and evaluation interfaces.

The repository has several observable output channels. In this audit, *submitted* means returned by the reviewer, *finalized* means emitted after projection and merging, and *delivered* means the exact ordered channel chosen for the author or evaluation. Existing runs that only record review, verified, or diagnostic channels establish what the software produced. Actual author receipt and usefulness require separate evidence.

## Findings that change the input, output or score

### 1. A review prompt can reveal a later title

The episode builder labels the fetched title `source_current_value_unverified`. The lead, solo and arm adapters pass its text to the reviewer. Comparing post-cutoff rename events with released titles identified substantive differences on **6 of 60 validation PRs, 1 of 60 evaluation PRs and 1 of 16 dev-medium PRs**, ignoring whitespace and Bors prefix changes. Validation PR 28922 tells the reviewer the PR is obsolete and names its successor. On 35636 the wording changes from weaker to stronger hypotheses. The affected inputs are real. The effect on a particular prediction is unknown. [Episode construction](../../src/mathlib_review/release/episode_builder.py#L334) · [Lead and solo inputs](../../src/mathlib_review/review/runner.py#L479) · [Arm adapter](../../src/mathlib_review/review/task_adapter.py#L31) · [Released title on 28922](../../inputs/pr_review_v4/releases/val-2025-06-2026-03-v1/input/episodes.jsonl#L15) · [Recorded rename](../../data/pull_requests/pr/28922/timeline.jsonl#L7)

Reconstruct the title at the same boundary as the diff and description, using rename events in reverse order. Omit fields whose value at that time cannot be established. Make the common reviewer-input projection own this decision. Test the actual rendered prompts, including the absence of the successor number on 28922. Issue a successor release and identify affected historical comparisons by episode.

### 2. The release and scheduler each narrow the PR population

The release uses final file counts and size, excludes reverts and toolchain-only changes, and requires qualifying Lean content. This selects on a later state and omits real work such as documentation and CI requests. The runner then filters *work units*, derives the PR set from the survivors, and builds solo tasks only for episodes represented in agenda proposals. In a local fixture, two PRs were requested and both episodes existed. Only the first had a work unit. Selection silently returned that PR alone. A whole-PR reviewer can read the second diff. [Release filter](../../src/mathlib_review/release/episode_builder.py#L241) · [Work-unit selection](../../src/mathlib_review/review/runner.py#L362) · [Solo task creation](../../src/mathlib_review/review/runner.py#L533) · [Real requests outside the release](icml-research-direction-2026-11-23.md#prs-the-current-benchmark-cannot-assess)

Choose the intended population at the episode boundary, using review-time attributes. Record a disposition for each requested PR. Generate zero or more units inside designs that need them. Exercise the normal plan with a mixed present/absent selection, a prose-only change and an empty change graph. Account for every requested episode. Keep the frozen Lean cohorts as named comparison populations and include quiet PRs and AI-assisted contributions in an independent broader evaluation.

### 3. A submitted request can disappear at anchoring

The solo projector emits a candidate for a resolved target. For an unresolved line, the anchoring trace retains a claim snippet of at most 200 characters. In one saved validation run the reviewer submitted **24** findings, **19** anchored and five had unresolved lines. Only the 19 continued to finalization. The third trace row contains an actual request. This can change estimates of the reviewer's ability even if the request would ultimately have been declined for delivery. [Projection](../../src/mathlib_review/review/candidates.py#L539) · [Finalizer input](../../src/mathlib_review/review/runner.py#L780) · [Saved counts](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/anchoring_report.json) · [Claim traces](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/anchoring.jsonl#L3)

Persist each submitted comment with its ordinal, full text, requested action and episode before resolving anchors. Attach zero or more locations and record unresolved ones. Delivery can then consider a PR-wide question, a cross-file request, or an inaccurate line explicitly. Replay the 24 submissions and require 24 full records, each traceable to a delivery disposition.

### 4. Verification changes meaning between investigation and delivery

The evidence collector treats a hit on a cited name as support for some duplication and generality claims. In a saved review the channel list includes `verified` for generalizing `exists_long_peano_curve` to all nonempty compact metric spaces. The supporting assertion records finding a file declaring one of eight cited names. That does not establish the proposed generalization. The structured reviewer likewise accepts a nonempty name lookup as verification of a duplication check. [Collector](../../src/mathlib_review/evidence/evidence.py#L494) · [Structured check](../../src/ape/tasks/lean_tasks/formal_math/review/structured.py#L612) · [Final finding](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/findings.jsonl#L1) · [Saved assertion](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/evidence/assertions.jsonl#L5)

The reverse occurs too. In a structured dev run, 29 ledger filings marked verified yielded 28 exact PR-and-claim matches in finalized rows. All 28 were classified as `model_assertion` and review-only. For PR 33066 the ledger records a successful compile for the proposed `coe_symm_auxIsometry` change. The structured projection strips edit/check fields and the solo conversion rebuilds the candidate. [Projection](../../src/ape/tasks/lean_tasks/formal_math/review/structured.py#L665) · [Conversion](../../src/mathlib_review/review/runner.py#L802) · [Saved ledger](../../results/pr_review_v5/runs/probe_dev_structured_gpt52_Grc_contract2_rep1/ledgers.jsonl#L1) · [Final finding](../../results/pr_review_v5/runs/probe_dev_structured_gpt52_Grc_contract2_rep1/findings.jsonl#L2)

Make a check identify its proposition, subject, workspace revision and outcome. Link the edit or lookup result to the original comment by ID. A substitution that elaborates at a real caller supports an applicability claim. Whether its benefit warrants asking the author remains a reviewer decision. Replay the irrelevant name hit and the successful edit. Require exactly the evidence established in each final record.

### 5. Conflict resolution can suppress compatible requests

The merger groups different actions by PR, primary change and concern family. Equal warrant can send every member to diagnostics. In the saved validation run two findings concerned distinct Finset declarations, `card_le_card_div_right` and `card_le_card_div_self`. Sharing a projected anchor made them an unresolved conflict. Both could be considered independently. [Conflict rule](../../src/mathlib_review/review/merge.py#L313) · [Two findings](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/findings.jsonl#L3) · [Conflict emitted](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/conflicts.jsonl#L1)

Make the relation explicit. Multiple sources can support the same request, two edits may be alternatives for the same decision, and two requests can coexist at one location. Preserve the submission-to-delivery mapping in each case. Demote for incompatibility only when there is evidence of it. Put this pair, a true duplicate and mutually exclusive edits in the same replay.

### 6. Precedent search can display the wrong code beside a real review comment

The index encodes context from the end of the original hunk but saves only its first 1,200 characters as metadata. The tool displays the tail of that prefix as the commented-on code. Joining the 43,736 indexed rows to the manifest's corpus found **12,728 non-author rows** where the truncated prefix ends differently from the original hunk. PR 27511, comment 2312680130, has a 6,801-character hunk. This counts mismatching endings in the index. Exposure in a run depends on which results the reviewer read. [Metadata](../../src/mathlib_review/retrieval/precedent_index.py#L243) · [Encoder input](../../src/mathlib_review/retrieval/precedent_index.py#L293) · [Displayed result](../../src/ape/tasks/lean_tasks/formal_math/review/context_tools.py#L268)

Extract the review-side window before truncation. Retain event ID, side, original line range and window digest. Rebuild and version the metadata, then compare displayed excerpts against the source for long left-side, right-side and multiline comments.

### 7. Corrected recall can count an excluded hit

The corrected view removes ruled-out obligations from its denominator but divides the original hit totals by that smaller set. For `iter_ds41_conv_dev_base_rep3`, PR 33321 is both a hit and an excluded obligation. The report gives **7/22 (31.8%)**. Counting hits among those 22 gives **6/22 (27.3%)**. The raw 7/23 belongs to the original population. The same error affects issue and resolution recovery in another saved run. [Eligibility calculation](../../src/mathlib_review/analysis/report.py#L223) · [Numerator and rates](../../src/mathlib_review/analysis/report.py#L395) · [Saved matched obligation](../../results/pr_review_v5/audits/iter-ds41-conv-dev-base-rep3/semantic_report.json#L135)

Filter obligation records by ID once and compute counts, numerators and denominators from that set. Apply the same operation before and after publication. Recompute historical derived views against both an excluded hit and an excluded miss. Retain the instrument's original recorded results.

### 8. An incomplete run can enter an ordinary comparison

The conditions report checks judge identity and obligation IDs but accepts a forensic audit. Comparing `pr5_patchset_qwen_3pr_rep1` with `pr5_patchset_gpt52_3pr_rep1` returned 0 versus 1 issue hits out of six with no top-level warning. The Qwen audit explicitly says `forensic: true`. All four partial audits among 137 examined had a complete partner that passed those checks. A failed session and a successful review that found nothing are different observations. [Comparison gates](../../src/mathlib_review/analysis/report.py#L581) · [Forensic audit](../../results/pr_review_v5/audits/pr5-patchset-qwen-3pr-rep1/semantic_report.json#L36)

Define comparison eligibility from the completed PR population including controls, instrument and version, pairing tiers, rulings, output channel and completion state. Make forensic comparison an explicit diagnostic mode with coverage beside the number. Replay this pair and an ordinary complete pair.

### 9. The matching instruments have different witness failures

The raw-ask matcher accepts `reached` with no finding index, even when the reviewer returned zero findings. A local empty-review fixture passed validation and unblinding credited **1/1 reached, 0/1 published**. A scan of 112 saved match files found indices on all 5,786 reached and 1,572 partial rows. This is a reproduced validation gap. [Raw-ask validation](../../src/mathlib_review/judge/ask_matching.py#L348) · [Unblinding](../../src/mathlib_review/judge/ask_matching.py#L428)

The semantic judge has a different failure. The heldout pipeline requests relation-tier pairing on a release without the relations file. The judge substitutes an empty list. Across 137 saved pair files all 2,809 observed pairs were anchor tier. The count alone does not identify which configurations requested widening. Under widened pairing the location-hit statistic also counts any paired finding. [Pipeline request](../../configs/pipelines/heldout12_judged.yaml#L40) · [Judge fallback](../../src/mathlib_review/judge/runner.py#L327) · [Location accounting](../../src/mathlib_review/judge/semantic_judge.py#L405)

Require a delivered-finding witness for positive raw-ask verdicts. Label witnessless historical records when reading them. Preflight relation capabilities, distinguish missing files from complete empty graphs, and compute location hits by the exact-anchor predicate. Test an empty review, a genuine relation-only match and a missing relation file. Preserve the distinct meanings of raw-ask and atomic-obligation recovery.

## Findings affecting execution and reproducibility

### 10. A sealed generation plan can accept a different reviewer

With the same solo config and agenda, changing the available context tools to an empty list or changing the solo dollar cap produced a byte-identical plan. Changing model temperature changed only the scaffold digest and the derived plan hash. The resume guard accepted it as an operational revision. Toggling the real `task_config.review_notes` intervention in the dev configuration produced the same acceptance. The guard exempts the entire scaffold digest because retries and timeouts live in it. The solo task takes its grants and caps from fields outside that digest. [Solo task inputs](../../src/mathlib_review/review/runner.py#L533) · [Resume exemptions](../../src/mathlib_review/review/runner.py#L1545) · [What is sealed](../../src/mathlib_review/review/runner.py#L1676)

Make the plan serialize the resolved reviewer inputs used at dispatch, including instructions, grants, model/route parameters, sampling, budgets and review policy. Keep an explicit allowlist for operational revisions and record the revision that produced each sample. Check that grant, temperature and notes changes fork the experiment, while retry-only changes can resume it. Budget increases across attempts should remain visible to comparisons.

The order of operations also matters. On partial resume the runner requeues failed samples and removes closed output files before building and comparing the incoming plan. An incompatible model or pinned input can therefore be refused *after* the old run has been reopened. Check compatibility without side effects before clearing results or changing scratch state. A rejected resume of a temporary partial run should leave the previous artifacts byte-for-byte intact. This consequence follows from control flow. [Reopen and cleanup](../../src/mathlib_review/review/runner.py#L1888) · [Validation order](../../src/mathlib_review/review/runner.py#L2077)

### 11. A generation budget buys more samples than its preflight counts

On the solo path the preflight prices one sample per PR in both dollars and tokens. The orchestrator schedules `execution.sample_count` slots per task. A local check accepted one PR with three samples, a $1.50 per-sample cap and a $1.50 total cap. The configured slots allow $4.50 in per-sample ceilings. This is possible exposure, not a measured charge. Generation then projects the task aggregate, so the additional samples are also a poor way to request independent review replicates. [Token calculation](../../src/mathlib_review/review/runner.py#L1274) · [Dollar calculation](../../src/mathlib_review/review/runner.py#L1459) · [Slot scheduling](../../src/ape/orchestration/orchestrator.py#L280) · [Aggregation](../../src/ape/orchestration/worker.py#L703)

For the existing one-review-per-PR output, reject generation `sample_count != 1` and retain separately named repetitions. If multisample generation is needed, count the slots before dispatch and carry sample IDs through delivery and judging. The replay runner already accounts for its sample multiplier and APE already exposes sample products. Test two PRs, three samples, one failure and both budget denominations. [Replay budgeting](../../src/mathlib_review/review/replay.py#L622) · [Per-sample outputs](../../src/ape/orchestration/products.py#L57)

### 12. A recorded coordination policy can disagree with what ran

One lead plan records subtractive synthesis but independently sets `apply_lead_synthesis` false. Its finalization report says that 23 assessments, including 11 drops, were received and synthesis was disabled. In a different run the plan sets a two-wave maximum and the journal for PR 30641 records wave three. A third-party reader cannot treat the policy block as a description of the intervention. [Plan construction](../../src/mathlib_review/review/runner.py#L1531) · [Execution](../../src/ape/tasks/lean_tasks/formal_math/review/lead.py#L505) · [Saved policy](../../results/pr_review_v5/runs/probe_postcutoff_lead_rep2/run_plan.json#L41) · [Finalization](../../results/pr_review_v5/runs/probe_postcutoff_lead_rep2/finalization_report.json#L87) · [Third wave](../../results/pr_review_v5/runs/probe_val_small12_lead_carried_calib/lead_journals/leanprover-community_mathlib4_30641_round1_56ea25b05f70fa368da076c50bcfd945cef4aaf2.jsonl#L14)

Resolve coordination once and give that policy to the planner, lead and finalizer. Distinguish assessed decisions from applied ones. Replay the journals and check actual wave IDs, number of jobs, drops applied and the source of each surviving comment against the policy.

### 13. A pipeline can preflight a malformed judge configuration

The graph builder hashes the bytes of each child YAML. The downstream preflight reports “config loads, paths derive” without invoking that stage's loader. A local fixture set the judge YAML to the invalid text `dataset: [`. With generation stubbed to avoid any model work, preflight reported success for the judge. Inherited base configurations can also change while the direct child's file digest stays the same. [Graph construction](../../src/mathlib_review/review/pipeline.py#L86) · [Preflight report](../../src/mathlib_review/review/pipeline.py#L240) · [Actual judge adapter](../../src/mathlib_review/review/stage_adapters.py#L52)

Give each adapter a side-effect-free resolve operation using the same loader and overrides as execution. Hash the resolved semantic inputs and validate downstream schemas before starting the expensive stage. Defer only checks that actually require its outputs. Test malformed YAML, an unknown field and a changed inherited base at the pipeline entry point.

### 14. A torn journal tail hides good records written after restart

The append-only writer appends straight to the file. The reader stops at its first malformed record. A temporary journal containing one valid row and a truncated second row, followed by a normal third append, returned only the first row. The stage ledger uses this pair of functions. A later action can succeed and remain invisible to audit and resume. [Writer](../../src/mathlib_review/io.py#L190) · [Reader](../../src/mathlib_review/io.py#L214) · [Stage ledger consumer](../../src/mathlib_review/run_state.py#L238)

Under a per-journal writer lock, detect a torn final frame before resuming, preserve its bytes for diagnosis and continue from the last valid boundary. Treat interior corruption as an explicit failure. Exercise crash, restart, and two independent stage completions against the same journal. The existing atomic immutable-file writer is appropriate for finished outputs. [Immutable writer](../../src/mathlib_review/io.py#L241)

## A design that follows what is being reviewed

**Use the contribution as the unit of review and the author's requested action as the unit of delivery.** The system already has most ingredients. `ReviewEpisodeInput` identifies the submitted state, `ReviewComponent` groups related changes, `InvestigationBrief` can express a question, the filing-contract reviewer can explicitly select the PR as its subject, and APE records samples and their products. Currently the common path converts these into arm responses. Give the common path the author's review as its native product. A specialist, an ordinary reviewer and a reviewer assisted by learned proposals can then all satisfy the same contract. [Components](../../src/mathlib_review/agenda/components.py#L16) · [Investigation brief](../../src/ape/tasks/lean_tasks/formal_math/review/lead.py#L52) · [PR-scoped filings](../../src/ape/tasks/lean_tasks/formal_math/review/filing_contract.py#L177) · [Registered designs](../../src/ape/tasks/lean_tasks/formal_math/review/__init__.py#L60)

| Responsibility | Input and owned output | What becomes easier to change |
|---|---|---|
| Collect and reconstruct | Source events and revision history → one dated episode, with field-level provenance and a record for each missing input. A reference extract can later attach human requests to that episode. | Change the sampling population, fix an as-of projection or add a training source without changing what is given to the reviewer by accident. |
| Propose and investigate | A reviewer or proposal source opens a question about the PR, files, declarations or callers. Record the concrete alternative if known, evidence for and against it, and why the investigation closed or stayed open. | Replace historical retrieval with a learned proposer, or use a specialist for one Lean check. Work that spans declarations can stay with one owner. The whole-PR reviewer can initiate questions the proposal source misses. |
| Check | A subject, proposition and workspace version → an observation such as “name resolves”, “replacement elaborates at this caller”, “counterexample found” or “environment incomplete”. | Add a new operator or retire a heuristic without changing the meaning of a previously verified claim. A lookup, compile and recommendation can each have a different outcome. |
| Decide and deliver | The reviewer decides whether to ask for an edit, request an explanation, suggest a redesign or return no comments. Save the ordered submission, versioned delivery policy, and exact ordered output with lineage to each source. | Change merging, limits, wording or ranking and replay the same submission. Rejections, duplicates and legitimate silence remain inspectable. |

## Promoting an experiment into the harness

The current generation driver is 2,303 lines, the shared review task base 1,257, the review CLI 1,230 and the probe module 1,394. Their size matters where a change has to be expressed several times. A new tool grant, for example, affects the prompt, what the worker can call, plan identity and reporting. The missing solo grant in the plan is a concrete case of these copies diverging. Ownership can be tested with one new intervention. A proposal source should define the dated material it supplies and how to render it. The task should consume that material through the existing input-file or stage interface. The plan should derive its identity from those resolved inputs. The scorer should see the same ordered review schema regardless of which proposal source ran. [Input resolution](../../src/mathlib_review/review/inputs.py) · [Existing design extension point](../../src/ape/tasks/lean_tasks/formal_math/review/__init__.py#L60)

A probe is ready for reuse when a second consumer can invoke it with explicit inputs, obtain a result with source and version identities, and reproduce the original recorded example through the shared code. Keep specialized selection and interpretation with the study. Promote a generic operation when it has an actual second consumer. For the historical-request exporter, that means parameterizing the census, cut date and reserved draws, giving it ordinary source-projection tests, and leaving the published pilot export reproducible. For a convention, keep the before-form, requested change, matched opportunity and independent held-out checks together. A frequency in an engineered situation alone cannot decide whether the reviewer should request the change on the next PR.
