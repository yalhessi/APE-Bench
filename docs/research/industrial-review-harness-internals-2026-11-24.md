# What industrial reviewers represent that APE currently loses

24 November 2026 · APE-Bench at `4cf97cd0`

A reviewer must decide what this PR changed, which expectations apply here, what still needs the author's attention, and how to express the request. APE has types for a change target, an investigation, an edit, a finding and a historical obligation. Several of those decisions nevertheless collapse into “the checker supports this finding” or “the matcher reached this ask.” An ordered submission, as proposed in the [implementation comparison](pr-review-harness-refactor-comparison-2026-11-24.md), would preserve the reviewer's output. The following changes address the quality and meaning of what goes into that output.

| Refactor decision | Existing APE owner | First case that should pass |
|---|---|---|
| Compare the same observation on the base and reviewed head before attributing it to the PR. | Change graph and evidence operators | PR 26718's unchanged category-theory notation cannot support a claim that the author introduced a lambda. |
| Express the source, force and exceptions of a review rule. | Convention catalogue, historical examples and finding evidence | On PR 32440 a declaration-local linter exemption is visible when judging that declaration. |
| Make the historical-example population explicit and let the reviewer follow the contributor’s cited sources. | Precedent index and PR context tools | A dated GitHub suggestion can be retrieved, and a cited predecessor PR can be looked up directly. |
| Let a reviewer use a private lead without filing its tentative fix. | Investigation brief and lead task | On PR 30458, noticing duplicated variable context can survive even if moving a section is rejected. |
| Judge what the final words ask the author to do and whether an offered patch completes that request. | Finalization, patch checks, raw-ask matcher | On PR 30641, asking whether an existing tactic works and asking to register a new lemma receive different action judgments. |
| Keep the disposition of each request distinct from the state of its discussion thread. | Historical discussion projection and follow-up evaluation | On PR 27971, revising one request leaves two formatting requests standing. |

## 1. Establish what the contribution introduced

Meta's Infer runs on code changes in review. In its public implementation, the report comparison groups ordinary diagnostics by issue hash in the current and previous analyses. The result writer emits introduced, fixed and pre-existing reports. A hash is an operational correspondence subject to collisions and moves. The important interface is that a downstream consumer gets a comparison, with the two reports available to determine its meaning. [Meta's deployment account](https://engineering.fb.com/2015/06/11/developer-tools/open-sourcing-facebook-infer-identify-bugs-before-you-ship/) · [Pinned Infer comparison](https://github.com/facebook/infer/blob/9a0955518f2605c334909b206bdbd2f78be8ef99/infer/src/integration/Differential.ml#L537-L551) · [Result writer](https://github.com/facebook/infer/blob/9a0955518f2605c334909b206bdbd2f78be8ef99/infer/src/integration/Differential.ml#L557-L581)

**A measured gap in APE.** The change graph stores the full paired entity text where available. The style operator runs over the reviewed text alone, and the style verifier can return support when that target contains a hit. I ran the existing `lint_target` twice per released target, first on `reviewed_code`, then with `base_code` in that same field. Within each target I intersected multisets of (rule code, exact line text), so moved line numbers did not create new observations. A missing side contributed no matches. Targets may overlap. These are counts of operator detections, not unique source lines or published findings. ## 2. Distinguish a rule's authority, its local applicability and the need to act

Anthropic's public Claude Code review plugin asks its guideline reviewers to identify applicable repository instructions and cite the rule they believe was violated. Its instructions tell them to disregard explicitly silenced checks. In GitLab Duo's version 4 review flow, the structured finding may carry a custom-instruction reference. The renderer uses that reference to attribute a comment to project policy. The renderer is formatting a supplied reference. It does not independently establish that the cited policy applies at the chosen location. Anthropic's plugin is a published command, and GitLab's flow is a versioned implementation. Neither source establishes a particular operating point for every hosted deployment. [Anthropic reviewer instructions](https://github.com/anthropics/claude-plugins-official/blob/5cec6716767283f4675a05f5f8855b5b49c81783/plugins/code-review/commands/code-review.md#L25-L48) · [Suppression guidance](https://github.com/anthropics/claude-plugins-official/blob/5cec6716767283f4675a05f5f8855b5b49c81783/plugins/code-review/commands/code-review.md#L80-L93) · [GitLab attribution code](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/ca9b96eb1a00d737ca92c48182b77edd6e23cf49/ai/features/review/code_review/components/findings.py#L215-229)

GA technologies' Kleene study shows why a thread citation alone gives a weak guarantee for learned conventions. In the authors' detailed analysis of 12 extracted rules, only two of the 56 clauses invoked in subsequent comments were explicit in the source discussion. For 38, the extraction added conditions to related material. For 16, the authors could locate no corresponding source. Moreover, 45 of 79 additional outputs citing those rules requested no change. That last observation matters even when a rule is faithful: the rule can apply and its objective may already be met. The study used a selected subset and author coding. Its small positive-case comparison does not establish a general advantage of extracted rules over the original threads. [Kleene, §§III–IV, particularly Table III and limitations](https://arxiv.org/html/2611.25918v1#S4.SS4)

APE already indexes explicit linters and library notes and measures adherence within a reference class. Preserve that work. When a finding invokes policy, let it refer to the **specific clause**, its dated source or inference, whether it is mandatory or advisory, and the applicable configuration at the declaration. On PR 32440, the reviewed patch changes a linter and adds four local exemptions for deprecated declarations in one file. A reviewer could reasonably question the exemptions themselves. Citing the global default as proof that the four declarations violate active policy is a different claim. For inferred conventions, keep the maintainer's words and the learner's reasons or exceptions distinguishable. On PR 33098 an expert's suggested edit actually retains the long form that a detector would shorten. [Catalogue fields](../../src/mathlib_review/conventions/catalogue.py#L103) · [Adherence](../../src/mathlib_review/conventions/catalogue.py#L324) · [32440 reviewed patch](../../inputs/pr_review_v4/releases/val-2025-06-2026-03-v1/input/episodes.jsonl#L34) · [33098 detector replay](../../results/pr_review_v5/probes/convention-detectors-2026-10-06/README.md#L124)

A concrete test pairs a known request with an independently selected exception. Hold the PRs and reviewer fixed and compare no guidance, the original dated passage and the extracted rule. Record separately whether the model identified the applicable source, whether there is an outstanding obligation, and what it ultimately asked the author to change. A rule that raises hits on the positives while inventing mandatory edits on the exceptions should stay experimental. This differs from another trial appending a convention list, which the project has already tested. [Previous convention experiments](../questions.md#conventions-and-knowledge) · [Stopped approaches](../dead-ends.md)

## 3. Treat the historical-example selector as part of the reviewer

The RevMate study at Mozilla and Ubisoft points to Mozilla's public `bugbug` implementation. At the revision current on the paper's stated access date, the retriever embeds the historical **code hunk** and attaches the human comment as payload. It queries the modified-file hunks on the new patch and keeps the best match for each comment ID. Before indexing, the Phabricator collector skips replies. A text filter excludes short and long comments, URLs, certain nits, fenced code and several phrases used in questions. The hunk must also resolve on a modified file. After generation, the writer's memory is cleared and a separate filter receives the raw diff and draft comments. Retrieved evidence is not explicitly handed to that filter. Each choice changes what kind of review survives. [RevMate, §III and reference 24](https://arxiv.org/html/2411.07091v1#S3) · [Study-era example selection](https://github.com/mozilla/bugbug/blob/6134ff622c1ee46f323439f77a08a18726912741/bugbug/tools/code_review.py#L458-L514) · [Reply exclusion](https://github.com/mozilla/bugbug/blob/6134ff622c1ee46f323439f77a08a18726912741/bugbug/tools/code_review.py#L545-L552) · [Retriever](https://github.com/mozilla/bugbug/blob/6134ff622c1ee46f323439f77a08a18726912741/bugbug/tools/code_review.py#L1281-L1318) · [Final filter inputs](https://github.com/mozilla/bugbug/blob/6134ff622c1ee46f323439f77a08a18726912741/bugbug/tools/code_review.py#L1180-L1210)

**What direct adoption would remove.** I applied the published text predicate, in source order, to the verbatim GitHub bodies of 1,140 agreed first-round requests in APE's 390-PR development export. Of 999 inline requests, **298** pass the text predicate. Of the 701 removed, 229 first fail the length test, 26 the URL test, 445 the fenced-code test and one the phrase test. **434 of the 445 fence exclusions contain GitHub suggestion blocks.** The other 141 requests appear in review bodies or PR conversation. Applying the further inline, thread-opening requirement leaves **257 of 1,140** eligible before any file or hunk check. Those requests cover only 167 of the 390 PRs. This is a counterfactual about historical example eligibility. It does not estimate RevMate's performance on Mathlib or the quality of its Mozilla suggestions. [Local development export](../../data/pr_review_v5/first_round_development_before_2026-01-01.jsonl) · [Export construction](../../results/pr_review_v5/adjudications/arm-coverage-val1000-2025-06-2026-03-v1/provenance/first_round_examples.py)

**Borrow the retrieval interface, audit the population behind it.** For each precedent collection, keep the event ID and first exclusion reason from raw discussion through example selection. Preserve the relationship between code, exact requested edit, reply and PR-wide rationale. Use a hunk as a query when the reviewer needs an idiomatic replacement. Use a different route for a question about the contribution's purpose. If an assessor can remove a library-backed claim, pass it the cited witness or restrict its authority to what its inputs can establish. Test whether a short rationale request, an actual suggestion block, and a top-level thread each remain accessible to their intended consumer. Separately measure retrieval rank and resulting first-pass advice. A larger corpus alone cannot fix an eligibility predicate. [Current precedent index](../../src/mathlib_review/retrieval/precedent_index.py) · [What existing Mathlib reviewers can retrieve](icml-research-direction-2026-11-23.md#what-the-reviewer-can-actually-retrieve)

There is a second route missing from the review task: **follow a reference explicitly supplied by the contributor**. The community PR-Agent reviewer enables ticket analysis by default at the inspected revision. Its ticket-compliance path compares the change to requirements drawn from linked work items. Its GitHub implementation deliberately skips a numbered item if it is a PR. On APE's 60-PR validation release, 41 PRs have verified descriptions. Twelve of those name earlier same-repository numbered items. All 15 distinct targets resolve to PRs in the historical listing. The relationship varies: a previous change that removed fields, a dependency, a continuation and a revived proposal require different readings. Blindly adopting the ticket filter would discard all 15 in this sample. Four of the 15 targets have a detailed local PR record. A listing establishes identity and creation time. Later text still needs a public version as of the cutoff. The count used explicit same-repo links and numbered references in HTML-unescaped, verified descriptions, deduplicated within each PR. All 15 source PRs existed by the focal reviewed head’s commit time. Across six of those source PRs, 134 fetched inline or conversation comments had an update time at or after that cutoff. Four were created earlier and edited later. Passing the PR creation check alone would admit future versions of text. Add a dated lookup by explicit reference alongside precedent search. ## 4. Let private clues do useful work without committing the author to an edit

RevMate's human UI distinguishes a suggestion a reviewer publishes from one they value privately as a review tip. At Ubisoft, historical examples had higher publication acceptance than code context (8.9% versus 5.3%). The order reversed for the broader outcome that included tips (24.5% versus 32.2%). That outcome measures how participants rated the suggestions. Whether a private tip improved the review the author ultimately received is a separate test. [RevMate, §§III-B and IV-B, Table IV](https://arxiv.org/html/2411.07091v1#S4.SS2)

APE already has an `InvestigationBrief` with a question, rationale, prior work and abstention condition. It is currently addressed to a particular arm. A lead or solo reviewer also needs a way to keep an observation when the proposed fix is poor. On PR 30458 the reviewer spotted duplicate variable context and suggested moving a section. The maintainer's requested use of local `variable […] in` needed a different edit. In a trial, give the same reviewer that private observation, the drafted finding, or neither. Match tool and time budgets. Retain which downstream check used the clue and score only the final author request. Stop if tips merely consume investigation time or displace better requests. This can be tried with the existing brief and session products before adding any new public output channel. ## 5. Check what an author would understand and what accepting the patch would accomplish

Google's production comment-resolution assistant provides the inverse of comment generation. Reviewers reported that the generated edit sometimes misinterpreted their words. A later UI let them inspect the edit, refine the comment, or reject the edit while sending the comment. Several aspects of the deployment changed together, so the published adoption difference cannot isolate the preview's effect. Anthropic's public review command makes a related design decision: offer an inline suggestion when accepting it addresses the whole problem, and describe larger or multi-location fixes in prose. APE has an optional `ProposedEdit` and a coordinated `PatchSet`. Neither a valid location nor successful elaboration establishes that the displayed edit discharges the entire request. [Google study, §§4–6](https://storage.googleapis.com/gweb-research2023-media/pubtools/7525.pdf) · [Anthropic suggestion instructions](https://github.com/anthropics/claude-plugins-official/blob/5cec6716767283f4675a05f5f8855b5b49c81783/plugins/code-review/commands/code-review.md#L70-L78) · [Local finding and proposed edit](../../src/mathlib_review/schema/findings.py#L329) · [Patch check](../../src/mathlib_review/patchset.py#L307)

**A first evaluation with the saved output.** On PR 30641 the maintainer asked whether existing `gcongr` could discharge a step. The guided reviewer proposed registering a new monotonicity lemma to make it work. Both historical matchers credited that review. A reader shown only the final wording and the original PR should distinguish trying an existing tactic from changing the library's future tactic behavior. Ask that reader what action the comment asks the author to take, where its effects extend, or what answer would settle the question. Only then show the reference to the scorer. Calibrate the reading with blind human judgments. An automated reader measures its interpretation and needs validation before it can stand in for a contributor. [30641 report and original thread](icml-research-direction-2026-11-23.md#shared-api-design-as-a-worked-example) · [Saved proposed edit](../../results/pr_review_v5/probes/model-gap-val-small12/pr30641/TA1/tmp/gcongr_lemma.json)

For a renderer, use two complementary fixtures. On PR 33321 a one-line documentation suggestion is the complete edit. On 30458 a local snippet depends on changes to surrounding declarations and sections. The latter can be valuable evidence within one coordinated prose request. A one-click presentation should be available only when applying that particular patch suffices for the request as worded. A question may warrant no patch at all. ## 6. Reconcile requests against both the code and the conversation

GitLab Duo's version 4 flow carries the last reviewed head into context construction, does a separate lightweight prescan for surrounding code, then fetches existing discussions when a previous reviewed head is available. A tool-free review step receives the prepared context and discussions and emits a schema-validated answer. A deterministic step prepares it for publication. The reconciliation prompt tells the reviewer to enumerate the distinct points in an old comment and check each against the current code. It distinguishes dispute, obsolescence, partial repair and incorrect repair. This is more specific than recording a free-text reply or moving a comment to a new line. [Pinned flow and prescan](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/ca9b96eb1a00d737ca92c48182b77edd6e23cf49/ai/features/review/code_review/config/4.0.0.yml#L115-201) · [Reconciliation prompt](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/ca9b96eb1a00d737ca92c48182b77edd6e23cf49/ai/features/review/code_review/prompts/common/code_review_reconciliation/1.0.0.jinja#L1-19)

Reading the renderer gives a different answer to “will the author see it?” than reading the prompt. I passed one partially fixed item with one outstanding change to the pinned `render_previous_findings`. With its thread open, the function returned a bullet describing the remaining change. Given the same item and a resolved thread ID, it returned `None`. This controls the previous-findings **summary list**. It says nothing about the truth of the item or whether a separate new finding will be posted. APE should record thread state, observed changes to the code, the reviewer's judgment about each point and the final presentation separately. GitLab's instruction to accept a human dispute is a product policy; in Mathlib, the original maintainer sometimes explicitly upholds the request after a reasoned objection. [Renderer](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/ca9b96eb1a00d737ca92c48182b77edd6e23cf49/ai/features/review/code_review/components/findings.py#L180-211) · [Upstream regression cases](https://gitlab.com/gitlab-org/modelops/applied-ml/code-suggestions/ai-assist/-/blob/ca9b96eb1a00d737ca92c48182b77edd6e23cf49/ai/features/review/code_review/tests/test_findings.py#L255-300)

Two Mathlib fixtures reveal what a single `resolved` label would hide. On **27971** the reviewer revised the requested placement of a comment while retaining block formatting and backticks. On **28788** the same reviewer answered two “why?” replies on the same file and revision. Their justification for `protected` depended on a separate requested change to put the declaration in `namespace Nat`. Under that proposed naming, opening `Nat` could conflict with the existing root declaration. The submitted code still used `section Nat`. A reviewer following only one inline thread could miss that dependency. They described a separate `obtain` versus `rcases` request as taste. Replying, closing the thread and editing the code are three independently observable events. Even the existence of a counterargument does not determine the maintainer's response. [27971 exchange](https://github.com/leanprover-community/mathlib4/pull/27971#discussion_r2478464807) · [28788 submitted code](https://github.com/leanprover-community/mathlib4/blob/9fd589f5ddf34b21295ee0dfcf338fed3c566aa4/Mathlib/Algebra/Ring/GeomSum.lean#L279-L304) · [Namespace request](https://github.com/leanprover-community/mathlib4/pull/28788#discussion_r2296003007) · [Conditional collision](https://github.com/leanprover-community/mathlib4/pull/28788#discussion_r2296061643) · [28788 preference](https://github.com/leanprover-community/mathlib4/pull/28788#discussion_r2296092394)

Extend the discussion projection so each individual request can link to its prior finding, current code evidence and human decision. A historical “first review” still sees only material public at its cutoff. Keep the full contribution diff available alongside the delta since the prior review. ## What to change first

1. **Repair the deterministic claim first.** Compare base/head observations inside the lint operator, recognize Lean syntax and require evidence that matches the actual claim. Replay the paired-release cases and check all existing verifier callers. This can improve the correctness of an individual result without a model run.
2. **Make the evidence available to the reviewer inspectable.** Give precedent selection a dated inclusion rule and explicit exclusion counts. Preserve GitHub suggestion blocks. Add the explicit-reference lookup alongside hunk retrieval, starting with the 12 validation descriptions that name earlier work. Check what text was publicly available before making it model-visible. For an extracted convention, attach the clause that licenses the request and any local exception.
3. **Test recipient interpretation before introducing another generation stage.** Blind-read the paired 30641 requests and check the one-line versus coordinated-edit fixtures. Use a negative control where the right action appears only in investigation notes. Its author-facing score should be zero. Google's published Gemini review workflow illustrates how easily such a control can be missed: it invokes the PR-review command, while its evaluation adapts a local-review command and accepts matching words in stdout or tool arguments. On its logic-error fixture we reproduced passing assertions with only a directory-listing call and the word `input` on stdout. This is a property of those assertions, not an observed Gemini review. [Workflow](https://github.com/google-github-actions/run-gemini-cli/blob/c8bfcfc10cf7ec12752cbb35395598f2f2eb920a/.github/workflows/gemini-review.yml#L97-L126) · [Eval setup](https://github.com/google-github-actions/run-gemini-cli/blob/c8bfcfc10cf7ec12752cbb35395598f2f2eb920a/evals/pr-review.eval.ts#L14-L71) · [Assertions](https://github.com/google-github-actions/run-gemini-cli/blob/c8bfcfc10cf7ec12752cbb35395598f2f2eb920a/evals/pr-review.eval.ts#L80-L126)
4. **Keep private tips and dialogue reconciliation as controlled reviewer designs.** Use the same evidence, model, reviewer time and author reading depth across conditions. Require gains in the final first-pass review on fresh PRs, and report dialogue continuation separately. Preserve quiet PRs, AI-assisted contributions and PR-wide questions when defining both populations. A private tip may help another reviewer while never deserving an author-facing comment.

The offline checks establish the source-selection losses and the checker defect. The proposed reviewer changes still need a test of maintainer usefulness. The earlier [industry reading](review-refactor-systems-reading-2026-10-22.md) remains the reference for trained filtering and calibration at ByteDance, Atlassian and Google. The [migration plan](pr-review-harness-refactor-comparison-2026-11-24.md#migration-order-and-acceptance-criteria) covers independent repairs to submission preservation, scoring and execution.

## Verification and reproduction

The two corpus checks use the existing development export and released change graphs. The Mozilla text check was independently repeated by executing the pinned collector’s literal text predicate against the stored request bodies, preserving Markdown and line endings. The lint replay used the existing project Python and `ChangeTarget.model_validate` on every serialized target. Replacing only `reviewed_code` with that target’s `base_code` holds the operator and all other fields fixed. Count hits with a multiset of (rule, exact line text) on each side. Cases inspected in the evaluation release can serve as regression fixtures. A claim of improved review quality needs fresh PRs.

The GitLab rendering example exercised the pinned Python module directly with a synthetic one-item discussion. The Google assertion example exercised the pinned evaluation assertions with synthetic output. Both were local checks without a model or platform post. The APE lint-policy, convention-join and tree-lint test files passed (49 tests). No provider-backed reviewer or semantic judge ran for this study.
