# What to adopt from other PR review harnesses

24 November 2026 · APE-Bench implementation at `036bb42b`

The first change I would land is to make **one complete, ordered review submission replayable**. A reviewer should be able to ask about a PR's purpose, cite two declarations in one request, propose a cross-file edit, or return an empty review. The current path through work units, anchors and candidates can change what the author or evaluator receives in all four cases. Recording the original lets us change one part of the harness at a time and locate gains and losses. The [implementation audit](pr-review-harness-code-audit-2026-11-24.md) covers the repository and individual defects. This companion identifies external precedents, interfaces and a migration order.

A second input defect has a different remedy. At release time the builder already distinguishes a verified description, genuine absence and an unrecoverable historical text. On PR 29842 the release explicitly withheld the description. The saved filing nevertheless quoted “no description provided” and asked the author to write one. This establishes propagation into finalized review-channel output. It does not establish what the historical description said or whether any real author saw the finding. ## What the external systems contribute

The [October comparison](review-refactor-systems-reading-2026-10-22.md) already covers trained filters, randomized agreement and deployment feedback. The comparisons here address concrete decisions in the checkout. The linked implementations show what their interfaces preserve. Where the evidence comes from a paper or engineering account, the results belong to its authors and evaluation population.

### Keep the original request when its line cannot be shown

reviewdog's filter retains the full diagnostic sequence with separate flags for policy selection, the file appearing in the diff, and the diagnostic fitting in diff context. Gerrit preserves an original comment across patch sets. Placement on a new revision can fall back to a file, disappear from that revision, or show the same UUID on several copied files. Those are distinct outcomes for one original comment. [reviewdog filter v0.21.2](https://github.com/reviewdog/reviewdog/blob/v0.21.2/filter/filter.go#L8-L41) · [Gerrit porting behavior](https://gerrit-review.googlesource.com/Documentation/user-porting-comments.html) · [Gerrit ported-comments API](https://gerrit-review.googlesource.com/Documentation/rest-api-changes.html#list-ported-comments)

**Adopt.** Persist each original with a sample/attempt and ordinal ID, full payload, text and a separate content digest. Identical comments can occur twice. A placement identifies the target revision, subject, side and range. A delivery policy chooses inline, file, review body or withholding and records the reason. When two originals become one comment, the delivered comment points to both and has its own text and digest. Keep actual platform receipt and human reaction as later events if observed. Test an unplaceable PR question, a true duplicate, mutually exclusive edits and the two compatible Finset requests currently demoted together. [Current projection](../../src/mathlib_review/review/runner.py#L780) · [Merge rule](../../src/mathlib_review/review/merge.py#L313) · [Saved conflict](../../results/pr_review_v5/runs/probe_val_small12_gpt55_Grc_rep1/conflicts.jsonl#L1)

### Account for the work selected and the contents actually shown

Alibaba's open-code-review shares selection between preview and execution and records completed, reused, failed and waived work. Its session comparison uses coverage to distinguish a previous comment disappearing on reviewed work from a file the later session never reviewed. Its legacy fallback treats disappeared comments as resolved when the later manifest is missing. APE should mark execution coverage unknown where the archive cannot establish it. Use the same selection principle at APE's episode level. Select the dated PR first and create optional specialist work inside that review. Test the normal planner on a mixed selection containing a Lean change, a workflow-only change, an episode without work units and a missing episode. Each gets a disposition. On rerun, non-repetition on comparable completed scope records what the later reviewer said. Human resolution requires separate evidence. [Alibaba selection](https://github.com/alibaba/open-code-review/blob/55899906abc6381ad08f92a81ea2db50c56c7cba/internal/agent/selection.go) · [Alibaba session comparison](https://github.com/alibaba/open-code-review/blob/f6379f71edba1e59dbc056e8f455df1f84396498/internal/session/compare.go#L25-L75) · [Local selection](../../src/mathlib_review/review/runner.py#L362)

PR-Agent's regular review requests a diff and omitted-file information. When optional large-PR chunking is enabled and coverage is incomplete, its reviewer records partially included and wholly omitted files. APE's solo and lead already include the full **stored** episode diff. The unmeasured distinction here is which PR fields, callers, historical discussions and tool excerpts were available, initially shown or returned in response to a query. Extend the existing prompt-scope and pinned-input records at actual rendering and tool return. Use content references to avoid duplicating whole workspaces per session. These records establish exposure. Reviewing the output and tool choices gives separate evidence of consideration. A proposal to chunk reviews should be a budget-matched experiment on large and cross-file changes, with whole-PR reading as its control. [PR-Agent review entry](https://github.com/The-PR-Agent/pr-agent/blob/fe4a9fc140c485f1cfaf02af5bf39753658b5f73/pr_agent/commands/pr_reviewer.py#L1566-L1604) · [Serialized coverage](https://github.com/The-PR-Agent/pr-agent/blob/fe4a9fc140c485f1cfaf02af5bf39753658b5f73/pr_agent/commands/pr_reviewer.py#L2124-L2125) · [Local input sealing](../../src/mathlib_review/review/inputs.py) · [Declared prompt scope](../../src/mathlib_review/schema/identity.py#L350) · [Solo](../../src/ape/tasks/lean_tasks/formal_math/review/solo.py#L429) · [Lead](../../src/ape/tasks/lean_tasks/formal_math/review/lead.py#L379)

### Record what a check establishes and who decides whether to act

Mathlib's style action has a check path that runs `lake exe lint-style` and a suggestion path that generates a fix patch for reviewdog. Tricorder gives analyzers explicit prerequisites and collects developer feedback. Alibaba's filter prompt limits removal to claims the diff demonstrates are wrong. RovoDev separately assesses factual correctness and uses a trained actionability model. These illustrate how to assign authority when one piece finds a fact and another decides whether to ask for a change. A current Mathlib workflow alone does not establish which findings were already visible on a historical PR. [Mathlib action](https://github.com/leanprover-community/lint-style-action/blob/master/action.yml) · [Tricorder paper](https://research.google/pubs/tricorder-building-a-program-analysis-ecosystem/) · [Alibaba filter prompt](https://github.com/alibaba/open-code-review/blob/55899906abc6381ad08f92a81ea2db50c56c7cba/internal/config/template/prompts/review_filter_task_user.md) · [RovoDev paper](https://arxiv.org/html/2601.01129v1)

**Adopt.** A check identifies its proposition, subject, revision, prerequisite, outcome and witness. “A name resolves”, “the replacement elaborates at caller X”, and “edited A and dependent B rebuilt together” support different claims. Preserve contradictory evidence and indeterminate outcomes. Reuse edit and evidence records, and pass their identities through the structured adapter. Replay the unsupported Peano-curve generalization, the successful check dropped on PR 33066 and a two-file fixture where B can see a stale compiled A. Track the useful requests suppressed by any prospective actionability filter alongside its removals. [Collector](../../src/mathlib_review/evidence/evidence.py#L494) · [Structured projection](../../src/ape/tasks/lean_tasks/formal_math/review/structured.py#L665) · [Patch verification](../../src/mathlib_review/patchset.py#L307)

### Freeze what the reviewer can read and let scoring evolve independently

Two unrelated projects use the name ReviewBench. LangChain describes a local GitHub stub serving frozen PR data, a seeded repository, a submitted review and a hidden verifier. A valid extra can count toward precision while leaving coverage of the original curated issues alone. GitHub's released matcher maps submitted findings to reference issues and counts covered references once. Its matching groups by file, and its grounded precision view omits unmatched candidates. In Mathlib one request can span a PR or a family of declarations, and two duplicate comments still cost the author two interruptions. [LangChain's implementation account](https://www.langchain.com/blog/evaluating-code-review-agents-with-reviewbench) · [GitHub's matcher](https://github.com/review-bench/ReviewBench/blob/86b8fd643e7bbcf41d1cdddd54cc450a420075d1/scripts/eval/matcher.ts#L327-L368) · [GitHub's scoring methodology](https://github.com/review-bench/ReviewBench/blob/86b8fd643e7bbcf41d1cdddd54cc450a420075d1/docs/METHODOLOGY.md)

**Adopt.** The same dated case supplies every generation route. Show only text known to be public at the cutoff. Preserve the reason when a field was genuinely absent or its historical value could not be verified. The evaluator alone reads reference requests and later replies. Keep the full mapping from delivered comment IDs to eligible obligation IDs, including multiple witnesses, explicit nonmatches and PR-wide scope. Calculate each numerator from the same eligible ID set as its denominator. Score issue recognition and the requested action separately. Sample unmatched comments for blinded maintainer judgments of correctness and usefulness, record duplicate burden, and retain an independent count of historical requests recovered in the first *k* delivered comments. In the saved exclusion example this gives 6/22 under the corrected eligibility rule, alongside the historical 7/23. Historical silence and a later edit each have several possible explanations. AutoCommenter's authors sampled apparent resolutions and manually checked them before estimating action taken. [Local report](../../src/mathlib_review/analysis/report.py#L395) · [Saved matched obligation](../../results/pr_review_v5/audits/iter-ds41-conv-dev-base-rep3/semantic_report.json#L135) · [AutoCommenter, §§4–5](https://homes.cs.washington.edu/~rjust/publ/code_review_automation_aiware_2024.pdf)

Inspect AI has another useful practice here. A retry creates a new log and can reuse completed samples by identity. Its scoring policy exposes unscoreable results. APE already owns execution and session products. Resolve actual prompt, tools, effort, workspace, sample count and stage configs before mutating anything. Persist a new attempt linked to its parent. Reuse products only when execution-relevant inputs match, with an explicit new condition for intentional changes. Compare completed PR rosters including controls and distinguish a completed empty review, missing response, failed execution and unscoreable result. Allow forensic comparison to show its own coverage. Test a malformed judge config and a resume with one changed tool grant at the same CLI used in production. [Inspect retries](https://inspect.aisi.org.uk/eval-logs.html#eval-retries) · [Scoring policy](https://inspect.aisi.org.uk/scoring-policy.html#unscoreable-samples) · [Pipeline preflight](../../src/mathlib_review/review/pipeline.py#L240) · [Local comparison](../../src/mathlib_review/analysis/report.py#L581)

## Review behavior worth changing

LangChain tested a reviewer that traced changes through callers and tests on a 20-task defect subset. That suggests a procedural baseline for whole-PR review. Our filing-contract study gives a reason to go further. A hand-read of 17 partial matches found ten where the reviewer proposed a plausible edit but missed the library's existing name, idiom or API, four where it missed a relevant tactic, and three requiring history or contributor intent. Requiring those reviewers to file more often would preserve the wrong advice. [LangChain experiment](https://www.langchain.com/blog/evaluating-code-review-agents-with-reviewbench) · [Saved 17-case reading](../../results/pr_review_v5/probes/filing-contract-2026-10-12/partial_reading.md) · [Prior results](../questions.md) · [Stopped approaches](../dead-ends.md)

ProofJudge supplies a closer technical comparison. Its judge sees the named declaration, PR title and changed files, with access to the historical Mathlib base and the selected revision's changes. The prompt withholds the initial/accepted label. The evaluator then pairs the two independently generated scores. On PR 11640, a judge reading the initial version identified the existing lemma that lets the proof use `H.restrictPreimage s`. Borrow the initial-only diagnostic. Can the reviewer find the exact declaration, establish that the replacement works at this call site, and use it in an actionable review? Run a second, candidate-supplied comparison on the same cases. If the reviewer succeeds only when given the candidate, inspect the unaided trace to distinguish failure to find that declaration from failure to connect it to the PR. On APE's PR 33066 the ordinary reviewer already recognized the duplication and favored retaining a named wrapper. A later replay compiled the real caller with the existing constructor. A remedy that only improves search misses that decision entirely. [ProofJudge, methods and example §0.3.1](https://arxiv.org/html/2608.20432v1) · [Judge input](https://github.com/SJCaldwell/ProofJudge/blob/5c335ca2369d0779ac4274e0c281b396d0d21f42/proofjudge/agent.py#L351-L377) · [Paired execution](https://github.com/SJCaldwell/ProofJudge/blob/5c335ca2369d0779ac4274e0c281b396d0d21f42/proofjudge/runner.py#L201-L219) · [Mathlib caller replay](../../results/pr_review_v5/probes/one-reviewer-table-2026-10-10/replay_api_clients.py#L54)

The research question is whether earlier maintainer exchanges teach a reviewer when evidence should change its advice on a new PR. Two cases make that question testable.

- **PR 16488.** A maintainer initially asked the author to delete what looked like a commented-out command. The author pointed to the workflow that enables it. The maintainer then requested documentation. The workflow and script were in the reviewed revision. A first-pass reviewer could check the consumer, withdraw the deletion and explain the dependency in one useful request. Record the expert exchange as an observed event. Record a reconstructed pre-review check as a derived example with its own witness. [Reviewed workflow](https://github.com/leanprover-community/mathlib4/blob/74305ab5deff79763b6bec5d8e18830112e4fe41/.github/workflows/bench_summary_comment.yml#L26) · [Revised request](https://github.com/leanprover-community/mathlib4/pull/16488#discussion_r1759963271)
- **PR 41930.** The unaided reviewer checked callers and delivered an empty review. The guided reviewer retrieved an endorsement of the proposed naming convention. The expert asked why the old names warranted changing. The discussion the author ultimately cited differs from that endorsement and is absent from the local index. A first-pass reviewer could ask for the deciding rationale. It cannot cite a message it never retrieved. On PRs 26526 and 27457 authors both defended local notation using precedent and the reviewers took different actions. A rule that always accepts cited precedent fails that pair. [Actual guided calls](../../results/pr_review_v5/probes/postcutoff-2026-09-29/pr41930/TA1/calls.jsonl) · [Unaided output](../../results/pr_review_v5/probes/postcutoff-2026-09-29/pr41930/T1/findings.json) · [Expert exchanges](icml-research-direction-2026-11-23.md#what-a-follow-up-reveals-about-the-first-request)

**Design to test.** A reviewer may record its provisional advice, evidence that could change it and its decision to keep, narrow, replace, withdraw or ask. An ordinary solo reviewer can still submit just a review. The exporter found 68 returning threads on 56 development PRs and 1,730 on 1,075 older PRs. These counts identify speakers and turns. Decisions need a substantive reply and attributable evidence. All 56 development PRs have reconstructed inputs. Only 10 of the 1,075 older PRs have the detailed local collection tier. An exchange usable for reply-conditioned learning may still lack the reviewed snapshot needed for a first-pass case. [Exporter](../../results/pr_review_v5/adjudications/arm-coverage-val1000-2025-06-2026-03-v1/provenance/reviewer_followups.py) · [Source coverage](icml-research-direction-2026-11-23.md#what-a-follow-up-reveals-about-the-first-request)

First compare decisions on fixed provisional requests with decisive evidence supplied, including evidence that upholds a request. Then test transfer to **fresh chronological first reviews**. Controls should include the ordinary whole-PR reviewer, a reviewer trained on initial requests, and the same historical exchanges supplied as examples. Match model family, training allowance where applicable, reasoning effort, tools, dated sources, inference budget and delivered comment budget. Keep each linked change series within a single split. Keep human-selected locations, later replies and future edits evaluator-side. Include flagged AI-assisted contributions, quiet PRs, and a separate population of previously excluded small, large, docs-only and tooling changes. Report expert-request recovery, useful comments displaced, duplicate burden and unsupported mandatory changes at a prespecified reading depth, with blinded judgments of unmatched advice and multiple repetitions. A gain that requires the author's later answer supports dialogue continuation. The first-review claim requires a gain with only the evidence available on the new PR. ## Migration order and acceptance criteria

| Order | Change | Acceptance through a normal entry point |
|---|---|---|
| 1 | Correct the known input and scoring errors independently. | Render PR 28922 without a later title and distinguish withheld from genuinely absent descriptions. Re-score the excluded-hit example at 6/22. Ordinary comparison refuses a partial/complete pair and accepts a comparable complete pair. |
| 2 | Dual-write ordered submissions and import what the archive supports. | The anchor fixture yields 24 full original records in order and 11 completed envelopes including the empty list and its message. The old projection still yields 19 anchored rows. The probe adapter preserves all 890 packet findings and can reproduce the historical 733-item projection. An unavailable original across all supported sources yields an explicitly incomplete import. Exercise solo, specialist, structured and lead paths. |
| 3 | Separate placement, evidence and delivery. | Every original has a disposition. A PR-wide rationale request can appear in the review body. Compatible Finset advice survives. A name hit and a checked edit preserve their respective evidence. Changing order or comment budget requires no regeneration. |
| 4 | Make execution identity, resume and failure explicit. | Crash after one sample of a repeated task. Resume identically and obtain one completed product per requested sample. Changing a tool grant or inherited config is detected before writes. A torn journal tail cannot hide the next success. Empty, partial and failed work have different outcomes. |
| 5 | Try the evidence-guided reviewer as a consumer of these interfaces. | First show appropriate changes of advice on supplied evidence. Then test independent first-pass reviews against the controls at equal reading burden, including quiet PRs. Check whether a gain displaces useful existing comments. |

The input and measurement corrections in step 1 can proceed alongside the first submission replay. Steps 1–4 have deterministic or saved-output acceptance cases. Step 5 is a research decision. Improving what the reviewer discovers, assessing technical evidence and preserving the advice it already produces can now be tested independently.

## Verification scope

The archive checks used saved data and the linked implementations. No paid generation, ingestion or semantic judging was run. The local suite with the project Elan toolchain reported 3,127 passes and two failures. Both failing config tests passed against a temporary view of the 193 tracked config files. The shared checkout includes three untracked Luna configs that trip those tests. Frozen-artifact verification passed for all 717 manifest references and 1,180 locked files. The external harness comparisons establish implementation options. Their effect on author-facing Mathlib review remains to be tested.
